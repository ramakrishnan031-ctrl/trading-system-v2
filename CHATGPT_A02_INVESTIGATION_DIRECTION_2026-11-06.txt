7. INVESTIGATION QUESTIONS — STUDY

Claude: trace the source and actual implementation; answer each question with evidence, or explicitly mark UNKNOWN / NOT ESTABLISHED.

A. Configuration inventory and provenance
1. What exact YAML and CSV files exist under config/ at the baseline, and which are A02-owned?
2. What is each file's purpose according to its own content, comments, docstrings or other intent sources?
3. Which files are required, optional, generated, historical, examples or apparently unused? Do not infer use from presence or filename alone.
4. Are there configuration sources outside config/ (for example environment variables, .env.example, command-line paths, constants or database-backed settings) that feed A02's configuration pipeline? Map them without expanding ownership of other topics.
5. Are any expected files absent from the baseline? Distinguish absence from proof of deletion or runtime non-use.

B. Parsing, schemas and validation
6. For each file format, identify the parser, schema, validation functions, validation order and caller.
7. What types, allowed values, ranges, units, required keys, optional keys and cross-field constraints are actually enforced?
8. Which values receive defaults, coercion, normalisation, fallback or silent substitution? Identify the exact source and precedence.
9. What happens for missing files, missing keys, unknown keys, malformed YAML/CSV, wrong types, invalid encodings, duplicate entries, empty values and partially valid configuration?
10. Are validation rules consistent between schemas, validators, loaders, auditors and actual consumers? Identify checks that are missing, duplicated, dead or contradicted.

C. Loading and effective settings
11. Trace the complete configuration load path from the entry point to the returned configuration objects, including CLI-supplied config paths and environment-variable names.
12. Establish precedence among file values, environment variables, command-line options, defaults, constants, database state and code overrides wherever supported by evidence.
13. Which settings are read at import time, process start, subsystem construction, per-session, per-signal or later? Identify caching, snapshots, reloads and stale-value risks.
14. Does the code use the configured value, transform it, ignore it, override it or use a different hardcoded value? Search all reads and writes by key/name; do not stop at the obvious loader.
15. Are settings read differently by different modules or processes? Map the consumer paths and cross-topic owner.
16. Which configuration values are genuinely effective in Live paths? Keep configured value and code-effective value distinct. Do not claim a runtime value was in force on the terminated VM.

D. Strategy configuration
17. Trace strategies/schema.py and strategies/loader.py: discovery, file selection, parsing, schema validation, enabled/disabled state, defaults, error handling, caching and returned objects.
18. Establish how strategy YAML values reach the strategy and screening consumers. A07 owns strategy selection, screening and trade-decision logic; A02 records only the configuration loading and handoff boundary.
19. Check whether all strategy files follow the schema, whether unknown or extra keys are accepted, and whether validation differs across strategy types or consumers.

E. Snapshots, hashes and configuration change handling
20. Trace core/config_snapshotter.py and every caller/consumer. What is included or excluded in the snapshot and why?
21. Establish how hashes are generated, stored, compared and interpreted; identify canonicalisation, ordering, encoding and path rules.
22. Trace core/config_auditor.py and all callers. Does it inspect the same source and effective settings as the loader? What does it report, and what does it fail to detect?
23. Establish behaviour for added, changed, removed, missing, unreadable and invalid configuration files, including failed starts and repeated starts.
24. Cross-reference A01 finding S-11 and A01's treatment of configuration-change detection. Do not re-decide Rama's Phase 2 treatment.

F. Temporary configuration mechanism
25. Trace scripts/revert_temp_config.py statically. What markers and file patterns does it recognise, what does it change, what confirmation or safeguards exist, and what are its failure/partial-write paths?
26. Establish whether the script is declared or invoked anywhere in the baseline. A declaration does not prove execution. Do not run it.

G. Security and environment-variable handling
27. Record environment-variable names, the code paths that read them, whether they are required/optional and their fallback behaviour. Never record their values.
28. Identify where credential-related keys are declared, loaded and consumed, by type and location category only. Do not reproduce values or infer that a key is a valid secret.
29. Check whether configuration snapshots, hashes, diffs, exceptions, logs or reports could expose secret values or sensitive configuration content. Describe the exposure path without copying any sensitive value.
30. Identify configuration files or fields that appear to contain sensitive material. Do not quote values; flag the path and field/key name only.

H. Cross-topic consumers and completeness
31. Build a key-to-consumer map for all A02-owned settings: source file/key → loader/validator → transformation/default/override → consumer path/function → downstream topic.
32. Search codebase-wide for reads, writes and aliases of A02-owned keys, including direct YAML/CSV reads that bypass the central loader.
33. Identify duplicate settings, competing sources of truth, inconsistent units/time bases, stale names, unused definitions and settings with no clear owner.
34. Cross-reference A01 handoffs C7d, C10a, C10b, C12, C35, S-11, S-24, W-17, M-19, M-20 and M-24. For each, state what A02 confirms, rejects or cannot establish, with exact evidence.
35. Identify further cross-topic handoffs discovered during A02. Assign ownership according to the approved index; do not reassign topics yourself.
