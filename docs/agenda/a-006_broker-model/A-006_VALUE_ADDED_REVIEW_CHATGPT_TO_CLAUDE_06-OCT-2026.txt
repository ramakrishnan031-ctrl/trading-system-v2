2. Q-27 — SHOULD EVERY INTRADAY TRADE USE MIS?
======================================================================

RAMA’S ANSWER: A — MIS for every intraday trade; if the instrument is
blocked for MIS, reject the intraday signal/order.

CHATGPT REVIEW: AGREED AS A V2 PROPOSAL.

This is clean and internally consistent.

Important distinction:

    "Every intraday strategy requests MIS"

does NOT mean “Every instrument is guaranteed to be eligible for MIS.”

Conceptual flow:

    INTRADAY STRATEGY
          ↓
    PRODUCT REQUEST = MIS
          ↓
    BROKER / INSTRUMENT ELIGIBILITY CHECK
          ↓
    MIS ELIGIBLE?
       YES → continue
       NO  → reject / do not submit as CNC automatically

Do NOT silently convert an intraday signal into CNC merely because MIS
is blocked. That changes the business meaning of the strategy.

Recommended V2 wording:

    "All V2 intraday strategies request MIS. If Zerodha does not permit MIS
     for the selected instrument at order time, the intraday trade is
     rejected rather than converted to CNC."

The exact pre-check mechanism remains OPEN for the later broker/order
design. Broker eligibility and product configuration are separate
concerns.

STATUS: PROPOSED V2 INPUT — accepted for now, not a final implementation
decision.

3. Q-28 — “DELIVERY MUST BE IN GTT” — WHAT DOES THAT MEAN?
======================================================================

RAMA’S PREFERRED ANSWER: A — normal CNC buy, then OCO GTT for stop-loss
and target after entry.

CHATGPT REVIEW: AGREED. OPTION A IS THE CORRECT INTERPRETATION FOR THE
INTENDED MODEL.

Recommended wording:

    "Delivery entry is a normal CNC buy. After the delivery position is
     confirmed as filled, the system creates/maintains a broker-side OCO GTT
     containing the delivery stop-loss and target."

Sequence:

    approved DELIVERY signal
          ↓
    CNC entry order
          ↓
    fill confirmation
          ↓
    verify actual filled quantity / average price
          ↓
    create OCO GTT for actual position
          ↓
    monitor/reconcile GTT state
          ↓
    target OR SL triggers
          ↓
    other OCO leg is cancelled by broker
          ↓
    reconcile final position

Do not create a GTT against an assumed quantity if the CNC entry was
partially filled.

Also preserve: - manual broker-side changes must be
detected/reconciled; - GTT creation failure after a delivery fill is a
protection failure requiring bounded retry/escalation; - exact GTT
construction remains a later G/order-design decision.

STATUS: PROPOSED V2 INPUT — accepted for now, not a final implementation
decision.

4. CHARGES — DO BROKER CHARGES MATTER FOR SIZING?
======================================================================

CHATGPT ANSWER:

Charges should NOT normally be an additional sizing deduction if sizing
is explicitly based on available cash / configured capital allocation
and broker-required margin.

Therefore I agree with Claude’s distinction:

    SIZING
       → use the defined capital/margin model
       → do not invent an estimated "charges reserve" unless later governance
         explicitly requires it.

    REALISED NET P&L / PERFORMANCE
       → actual broker charges matter.

    DAILY LOSS LIMIT / RISK REPORTING
       → define whether loss is gross or net of actual charges. If a control
         is defined as net loss, actual charges should be included.

    AUDIT / REPORTING
       → retain actual broker/order/trade charge evidence where available.

Do not use an estimated brokerage/charge amount as a hidden sizing
factor.

Recommended V2 wording:

    "Broker charges are not a separate capital-sizing input unless explicitly
     configured later. Actual charges are retained for post-trade net P&L,
     performance reporting and any loss-limit calculation whose definition
     is net of charges."

Exact API/source/timing for final charges should remain OPEN until the
order/reporting agenda is reviewed.

STATUS: PROPOSED PRINCIPLE — not a final implementation decision.
