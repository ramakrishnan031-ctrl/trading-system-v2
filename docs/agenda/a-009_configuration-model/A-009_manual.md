## 4. How AppConfig was loaded (FACT, SOURCE-VERIFIED)
- core/config_loader.py records six design notes: CL1 `load_all(config_dir: Path = Path("config")) -> AppConfig`; CL2 atomic load, "No partial AppConfig ever returned"; CL3 every model uses extra="forbid", so an unknown key fails; CL4 a SHA-256 hash per file in AppConfig.file_hashes; CL5 "No env-var interpolation, no includes. yaml.safe_load() only. Values needing env vars go in .env, read by consumer modules"; CL6 all schemas in one file, "Split into core/config_schemas/ if file exceeds 600 lines" (the file has 2,516 lines; not followed).
- The file registry (_CONFIG_FILES) lists 8 files. The holiday file name is built when the module is imported, from the current year: `f"nse_holidays_{_date.today().year}.yaml"`.
- Per file, in order: missing file, ConfigMissingError; read the raw bytes and hash them; yaml.safe_load (a YAML error becomes ConfigSchemaError); an empty file becomes {}; Pydantic validation (failures become ConfigSchemaError with the error list). All 8 must pass.
- Validators at load: the SystemConfig validator runs the config auditor's start-up groups and fails on a BLOCK finding (section 6); scoring thresholds must satisfy high > medium > min_pass; each scanner URL must be http or https; the trading-hours chain requires market_close <= service_window_end < 18:15.
- Stale documentation. The docstring says the loader "Does not fill in defaults for missing keys (CL3: extra="forbid", all required)"; in fact 23 SystemConfig fields and the scanner_type of 15 scanners took schema defaults at the baseline (section 8). The header lists "nse_holidays_2026.yaml" while the code uses the current year.
- Holiday file. Only nse_holidays_2026.yaml exists at the baseline. INTERPRETATION / AUDIT LEAD (code path, not observed; the system did not run into 2027): the first start in 2027 would fail to load (exit 5) unless a 2027 file had been added. main.py's holiday guard reads the same file separately through utils/holiday_guard.py (no schema) before logging starts; there a missing file is ignored ("missing holiday file: proceed with startup"), and load_all then fails. The pre-flight presence check treats a missing holiday file for the year as CRITICAL.
- --config. main.py uses `Path(args.config) if args.config else Path("config")`, a path relative to the working directory. The repository's systemd unit runs `main.py --mode live` from WorkingDirectory /home/ubuntu/systems/trading-system with no --config, so the service loaded that directory's config/. Whether the unit installed on the VM matched the repository copy is NOT ESTABLISHED (VMs deleted). HISTORICAL (Rama, Q4 30-Sep): UNKNOWN.
- No hot reload. Both loaders are load-once at start-up; a configuration edit took effect only at the next start. HISTORICAL (Rama, Q6 and Q31, 30-Sep): confirmed; every YAML edit needed a service restart.

## 5. Start-up sequence and failure behaviour (FACT, SOURCE-VERIFIED unless marked)
Start-up order in main.py (the configuration-relevant steps only; B-001 and B-002 own the full boot):
1. Argument parsing. Invalid arguments: exit 5.
2. Holiday guard, before logging: on a weekend or listed holiday it prints a message, sends one Telegram note per day and exits 0.
3. Service start window (FIX-189): outside [08:00, 18:15) IST it exits 0 before logging and before loading configuration. Bypassed by --status, --dry-run, --interactive, --resume or the environment variable TS_IGNORE_MARKET_WINDOW=1. The daily stop is the configured trading_hours.service_window_end (17:35 in production), enforced by an end-of-day self-exit thread.
4. Single-instance lock (failure: exit 1).
5. Phase 0b: load_all. Any exception: CRITICAL log line "Config load failed: …" with the error detail (detail added 25-Jul-2026), exit 5. ~~Then the usage tracker registers every loaded value (section 6).~~ (superseded by erratum E-2) Then the usage tracker registers the values of five of the eight AppConfig files (section 6).
6. Configuration-hash check against the session row, which is then rewritten at once with the new file hashes (section 11).
7. Phase 0d start-up checks. A blocking failure: exit 3. When the failure is invalid_strategy_configs, one Telegram and email alert names each bad strategy file first (18-Jul-2026).
8. Configuration snapshot (non-fatal; section 11).
9. Phase 0e: the subsystems and the notifier are built; the configuration-change alert is sent (section 11); the strategies are loaded; the auditor's group A is re-run with the strategies for two rules (A4 when structure exit is on; A5 when delivery_enabled is true, which it was in production), and a BLOCK there exits 3.
10. Phase 0h: the usage check (warn-only), a STARTUP event, and the session row updated.

systemd (repository unit): Restart=on-failure, RestartSec=10, RestartPreventExitStatus=3 4 5. A configuration failure (5), a start-up check failure (3) and a HALT (4) are not restarted; exits 1 and 2 are restarted after 10 seconds; exit 0 is not restarted.

## 7. Global versus strategy settings (FACT, SOURCE-VERIFIED unless marked)
- No general precedence rule existed. Each consumer combined the two levels in its own way. Relationships found in the source:
  - Entry windows: a strategy may enter only when both the global window (trading_hours) and its own window allow it; the global 10:00 start was a floor, so the strategies' 09:25 start never bound (A-008 section 7).
  - Product gates: global trade_type, force_intraday_only and delivery_enabled decide whether a strategy's declared intent can trade (A-007, A-008 section 6).
  - Position caps: a strategy's own maximum concurrent positions binds alongside the global max_open_positions (A-008 section 13).

## 11. Change detection and snapshots (FACT, SOURCE-VERIFIED unless marked)
- File hashes. load_all hashes the raw bytes of the 8 AppConfig files. check_config_hash compares them with the JSON stored in the session row (last_config_hash). On a first run or an unreadable stored value it reports no change.
- The session row is rewritten with the new hashes early in start-up ("MED #10": "before any crash-prone Phase 0d/0e code"), before the start-up checks; the CONFIG_DIFF event and the WARN alert "Config Changed Since Last Session", naming the files, are sent later in Phase 0e, once the notifier exists. INTERPRETATION / AUDIT LEAD (code path, not observed): if a start failed between these two points (for example a start-up check exit 3 after a config edit), the next start would compare against the already-updated hashes and no change alert would be sent for that edit.
- Coverage: the 8 AppConfig files only. Strategy YAMLs, preflight.yaml, cron_registry.yaml, accounts.csv and the other files in section 3 were not hashed or alerted.
- Snapshot (core/config_snapshotter.py, "W0"): after a successful start-up check, the loaded AppConfig is turned into JSON (model_dump), secret-looking keys with non-empty string values are redacted (markers password, secret, token, api_key, apikey; *_env names kept), the JSON is written with sorted keys and hashed with SHA-256, and a row goes into config_snapshots with the date, time, account, mode and trade_type. The same hash on the same date is skipped; a different hash on the same date adds a row. A snapshot failure is logged and never blocks start-up.
- FACT (RECORD-DERIVED, NI-6, 22-Aug-2026): the file hashes are inside the hashed JSON, so a comment-only edit changes the snapshot hash (measured: JSON 16,206 bytes and every value unchanged, hash "4bed2598…" to "1b163ca4…"). The module's rule: "A config_hash change is evidence that a config FILE changed. It is NOT evidence that a config VALUE changed."
- Strategy YAMLs are not in the snapshot. The resolved configuration is recorded, not the raw YAML.
- HISTORICAL (Rama, Q17 and Q18, 30-Sep): he does not recall using snapshots or seeing several on one day. Q19: YES, the files on disk and what ran did not always match, because changes were made on the PC or on the VM without being copied back (section 15).
