## 5. How secrets reached each process (FACT, SOURCE-VERIFIED unless marked)
- systemd units (repository copies): trading-system.service, alert-watcher.service, security-watcher.service and trading-watchman.service (the Gemini log monitor) each load `EnvironmentFile=/home/ubuntu/systems/trading-system/.env`. token-watcher.service runs as root with no environment file; its Telegram helper sources .env itself, ignoring a missing file (`. ./.env 2>/dev/null || true`). The GUI unit has none ("auth lives in backend/config/gui_config.local.yaml").
- Cron (repository crontab, generated from config/cron_registry.yaml): every Python job runs `set -a && . ./.env && set +a` before starting (FIX-189: SHELL=/bin/bash, values "EXPORTED into the child process"). Each run re-reads the file.
- python-dotenv: scripts/auto_refresh_token.py (`load_dotenv(_ROOT / ".env")`, so a manual run works) and scripts/zerodha_login.py (`load_dotenv()`, current folder). main.py has no load_dotenv.
- In-process: main.py copies the primary's account-specific API key into ZERODHA_API_KEY and the token file's value into ZERODHA_ACCESS_TOKEN.
- DEPLOYMENT.md (I.5, 25-Apr-2026): .env is created on the PC from .env.example, filled in, copied to the VM with scp and set to mode 600; the operator checks that the unit has the EnvironmentFile line.
- RECORD-DERIVED (03-Jul-2026, telegram_token_shadow_investigation): the unit installed on the VM referenced .env through EnvironmentFile and had two drop-ins in /etc/systemd/system/trading-system.service.d/: watchman.conf (no environment settings) and telegram.conf (modified 18-May-2026), which set TELEGRAM_BOT_TOKEN, TELEGRAM_CHANNEL_PRIMARY and TELEGRAM_CHANNEL_SECONDARY as `Environment=` lines. After the 02-Jul rotation the drop-in's token was a revoked one (a value-blind getMe returned 401; the .env token was valid). The record calls this the "same EnvironmentFile-shadow pattern as the webhook finding". It concluded that the drop-in overrode .env, so the main process held the revoked token while cron jobs used the valid one; it found no logged main-process failure ("a positive runtime failure line is not asserted"). Its fix (remove the values from the drop-in) was "Not done in this investigation"; no later record of the removal was found.
- CURRENT EXTERNAL FACT (systemd documentation, checked 2026-10-08): "Settings from these files override settings made with Environment="; the files are "read shortly before the process is executed"; without a "-" prefix, a missing, unreadable or invalid file makes the service fail to start. systemd issue #9788 records the maintainers keeping that order (EnvironmentFile wins over Environment=, drop-ins included).
- INTERPRETATION / AUDIT LEAD: under the documented order, the main process would have used the .env token, not the drop-in's revoked one, unless the drop-in also reset EnvironmentFile= (not recorded). The record's "split-brain" conclusion therefore rests on a reversed precedence assumption and is NOT ESTABLISHED; which value the process held was never measured. The drop-in remains a real defect: a second, divergent copy of a secret outside .env, outside the security monitor's default watch list and the repository's auditd rules, which covered the unit file but not the drop-in folder (section 14; the installed security.yaml watch list is not known).
- INTERPRETATION / AUDIT LEAD: three parsers read the same .env: systemd (no $ expansion; its own quoting rules), bash (`.` runs the file as shell code: $ expands, unquoted spaces split) and python-dotenv. CURRENT EXTERNAL FACT (PyPI, checked 2026-10-08): python-dotenv "can interpolate variables using POSIX variable expansion" and by default does not override variables already set (override=False). A value with $, quotes, spaces or backslashes could therefore differ between the service and the cron jobs. No incident is recorded; plain KEY=value lines read the same in all three.

## 7. Zerodha login, token lifecycle and manual fallback (FACT, SOURCE-VERIFIED unless marked)
- Daily chain (repository crontab and code): 05:00 daily `rm -f data_store/session/zerodha_token.json` (token_cleanup); 08:15 Mon-Fri auto_refresh_token (holiday skip that fails open: on a calendar error the job runs); token_watcher.sh polls every 30 seconds and starts trading-system.service when the token file is dated today, the IST hour is 08 to 15 and the last exit code allows a start ("05:00 delete -> 08:15 TOTP refresh -> token-watcher starts the app", per the script). The script's docstring still says 08:00; the crontab generated from the registry says 08:15, which settles the conflict A-006 section 9 recorded for the repository schedule (the installed crontab: Q-35 (a)).
- CURRENT EXTERNAL BROKER FACT (checked 2026-10-06, A-006): the Kite access token expires at 6 AM the next day. The 05:00 deletion removes only the local file; no logout call was identified.
- Headless login (FIX-187): account resolved from accounts.csv; POST user ID and password to kite.zerodha.com/api/login; TOTP from the stored seed (pyotp) to /api/twofa, retried once for clock skew; the request token taken from the Kite Connect redirect; exchanged for the access token with the API secret; saved through the same save_token as the manual flow. Network errors get up to 3 attempts (waits of 2 s and 4 s); an authentication error is final. Success: Telegram INFO and heartbeat SUCCESS. ## 8. Broker authentication failure during the session (FACT, SOURCE-VERIFIED unless marked; NOTE REQUESTED BY RAMA, Q33)

- broker/auth_recovery.py classifies an auth error as IP_NOT_ALLOWLISTED (order placement refused because the VM's public IP is not registered: "the token is VALID; do NOT invalidate it"), TOKEN_EXPIRED or AUTH_UNKNOWN. Per the module's docstring (its callers in the signal processor and the API-failure counter were not read): on an IP refusal the entry is rejected, reads continue (not IP-gated), the next signal retries, and the module builds an actionable CRITICAL alert body with the current public IP and the steps to update the Kite developer console. The pre-flight vm_ip_unchanged check alerts when the public IP changed since its last run (no automatic fix).
- broker/token_monitor.py (wired in main.py; 1,800 seconds; market hours only): calls the profile API. Only a genuine token-invalid result (TokenException, or a message classified TOKEN_EXPIRED) counts: CRITICAL log; one Telegram CRITICAL per episode, "TOKEN EXPIRED ... No new orders will be placed. Order monitor continues managing existing SL/TGT orders"; SOFT_KILL (reason token_expired). Network, server and rate-limit errors only log a warning (H-13); an IP refusal is not an expiry. It never re-logs in, never closes positions and never hard-kills.
