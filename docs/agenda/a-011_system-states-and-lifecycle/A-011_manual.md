## 3. The state model in one view (FACT unless marked)
The legacy system had no single RUNNING / STOPPED state. It had five layers, each held in a different place:

| Layer | States | Held in | Changed by | Across a restart |
|---|---|---|---|---|
| 1. Service process | systemd unit states (inactive, activating, active, deactivating, failed) | systemd | token watcher (start), systemctl stop, the process's own exit, Restart=on-failure | Process ends; the exit code steers what happens next (section 7) |
| 2. Start-up scenario | COLD, WARM, CRASH, HALT | Computed once per start from the session row, SHUTDOWN events, the EOD log and the kill state | detect_startup_scenario (section 6) | Decided afresh each start |
| 3. Trading gate (kill switch) | INACTIVE, SOFT_KILL, HARD_KILL; HARD_KILL flatten worker IDLE, RUNNING, DRAINING, COMPLETE | Memory (authoritative) plus one kill_switch_state row | The callers in section 8; resume; the clears at start | Row survives; cleared at start by date and reason rules (section 6) |
| 4. Time windows | Start window, entry window, cut-offs, service window end | Config and constants | The clock | Not a state |
| 5. Object states | Signals, trades, orders, GTT rows, EOD log, session row | SQLite | Many components | Persisted (section 15) |

Operator view: Rama remembers STARTING and STOPPING (section 4).

A normal trading day, as the code and records show it:
```
05:00  token file deleted (cron)
08:15  token refreshed (cron, Mon-Fri) -> token watcher sees a fresh token (hour 08-15, unit not
       active, no clean exit today) -> systemctl start trading-system -> main.py --mode live:
       holiday guard -> start-window guard -> instance lock -> config -> DB + kill switch
       -> clear prior-day kills -> clear scheduled kills -> scenario COLD/WARM/CRASH/HALT
       -> start-up checks -> token gate -> subsystems -> startup reconcile (twice)
       -> threads -> webhook -> STARTUP event -> "System Active" -> wait for shutdown
09:15  capital re-synced from the broker (if started earlier)
10:00  entry window opens          14:45  EOD pre-alert (if anything is open)
15:00  entry window closes         15:03 / 15:06  MIS auto square-off passes
15:15  force close: entry orders cancelled + SOFT_KILL (scheduled)
15:17  EOD square-off (backstop)   15:30  market close
17:35  self-exit gate: exit 0 when no flatten runs and no position needs the service;
       otherwise stay up, alert, re-check every 60 s
       cron keeps running on its own schedule (46 enabled jobs)
next trading day 08:15: the start clears the prior-day SOFT_KILL
```

## 6. Start-up scenarios, HALT and resume (Q9, Q13 to Q17, Q23)
- FACT (SOURCE-VERIFIED, utils/startup_checks.py detect_startup_scenario): (1) no session row: COLD; (2) HARD_KILL: HALT; (3) a SOFT_KILL triggered today: HALT (from an earlier day: fall through); (4) session date earlier than today: COLD; (5) same day: a SHUTDOWN event today gives WARM; otherwise an EOD square-off logged COMPLETE today also gives WARM; otherwise CRASH.
- FACT (SOURCE-VERIFIED, main.py and capital/kill_switch.py): two clears run before detection.
  - clear_stale_state (FIX-127) clears ANY kill triggered on an earlier calendar day: SOFT or HARD, scheduled or emergency. Its docstring records it as "Rama's 2026-06-20 decision" ("HEADLESS GUARANTEE": "a new trading day ALWAYS starts with a clean slate"; the safety net shifts to the EOD report's analysis of what was cleared). Each clear is audited as a KILL_AUTO_CLEARED system event.
  - auto_clear_scheduled_kill (FIX-154) clears a SOFT_KILL whose reason is one of the two scheduled reasons, "circuit_breaker_force_close_15:15" and "EOD_SQUAREOFF", even on the same day, when no trade is OPEN, PARTIAL or PENDING_FILL. It never clears a HARD_KILL; any other reason needs a manual resume.
  - So in practice HALT meant a same-day kill that survived both clears: a same-day HARD_KILL, a same-day emergency SOFT_KILL, or a same-day scheduled SOFT_KILL with open positions.
- HALT without --resume: CRITICAL log, exit 4. systemd does not restart 4. The token watcher does not restart a same-day exit 4 and sends one Telegram warning per day ("trading-system in HALT ... Fix root cause, then: main.py --resume"); after a prior-day exit 4 it makes one start attempt (fresh token, hour 08 to 15), which clears the prior-day kill.
- With --resume: the kill is resumed (reason "--resume flag", resumed_by "operator"), the start-window guard is bypassed, and the EOD self-exit gate is NOT armed, so a --resume start runs until it is stopped.
- deploy/resume.sh (FIX-188b): stop the unit, reset-failed, clear the kill in the DB with scripts/clear_kill_switch.py (a SOFT_KILL; a HARD_KILL only with --force), then start the unit under systemd (a normal start, self-exit armed).
- KNOWN AMBIGUITY: the token watcher's HALT warning tells the operator to run main.py --resume, while resume.sh's header says to use resume.sh instead of a standalone --resume.
- FACT (Q9): a blocking start-up check stops the start with exit 3 before any trading component starts.
- HISTORICAL (Rama, Q13 to Q17): --resume used (guess); "HALT" meant his stop command; HALT survived restarts; restart from HALT without an explicit resume happened the next trading day; he left it "halted" overnight after a manual stop. Against the source: in the code HALT is a start-up scenario, not the operator's stop; his next-day recovery matches clear_stale_state; a same-day kill survives a restart (HALT), a prior-day kill does not.

Against the source: since 20-Jun-2026 a prior-day HARD_KILL is cleared at the next start like any other kill; a manual resume (resume.sh with --force) is needed only for a same-day restart. Whether Rama's recollection reflects the rule before 20-Jun or the same-day rule: NOT ESTABLISHED.

## 26. Final A-011 statement
> The legacy system had no single RUNNING state. A systemd unit, started each morning by a token watcher after the 08:15 token refresh, ran one process that classified its start as COLD, WARM, CRASH or HALT, cleared the previous day's kills (every kind, by Rama's 20-Jun decision) and same-day scheduled kills when flat, reconciled with the broker before accepting signals, and then gated trading through a persisted, memory-authoritative kill switch (INACTIVE, SOFT_KILL, HARD_KILL) and time windows. SOFT_KILL blocked entries while exits continued; in the code path a scheduled SOFT_KILL at 15:15 closed each trading day and was cleared by the next start; HARD_KILL blocked new entries and dispatched a worker that tried to flatten intraday positions through its own exit path, with no flat book guaranteed, and, per the 03-Aug record, had never fired. At 17:35 the process exited itself once no flatten ran and no open position needed it; until 25-Aug-2026 a carried delivery position counted, which kept the process alive, prevented the next start and left the next day without entries unless the operator stopped the service by hand, as Rama describes. A stop, crash or HALT ended in-process management. Any protection then depended on the broker-side orders that actually remained active; the source does not establish that every residual position was protected, and the 03-Sep incident, with the process running, shows a path on which protection was lost and the emergency exit was rejected. Refusals at the webhook door left no signal row; queued signals were rejected with a recorded status on a stop or kill, and lost from memory on a crash. Cron ran its own schedule beside the service. Among the 46 lifecycle files compared, testing differed only by a log-only shadow, a force_qty sizing switch, line endings and configuration values, an earlier entry start among them.
