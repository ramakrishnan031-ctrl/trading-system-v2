## 7. Before application initialisation: the guards and what they leave on record
Three levels are kept apart (ChatGPT's 10-Oct review, point 2.8): systemd accepting a start request (with Type=simple the unit counts as started once the process is forked; section 5); main.py passing its early guards, which begins application initialisation (this section); and readiness, after configuration, state, broker and reconciliation (A-011 section 5, steps 5 to 17; B-002 to B-007, not redefined here). A start that systemd accepts can still end at a guard.
Order (A-011 section 5, steps 1 to 4): arguments, holiday guard, start-window guard, then logging and the instance lock. The detail:

### 7.1 Holiday and weekend guard (FACT, main.py)
- The date is `date.today()`, the host's local date, unlike the start-window guard, which uses the IST time authority (section 11).
- The trading-day test reads the holiday file for the current year (A-009 section 4). A missing file raises FileNotFoundError, which is passed ("missing holiday file: proceed with startup"), so start-up continues. RECORD-DERIVED: since 26-Jul the security watcher raises a CRITICAL while a required holiday file is absent (services table).
- On a weekend or listed holiday: a banner is printed (to the journal), one Telegram is sent per day (sentinel file logs/.holiday_notified_<date>, so a repeated start that day sends none), and main.py returns 0. The sentinel's comment: "token_watcher may restart the service multiple times on holidays; the sentinel prevents flooding the channel" (a comment, not a record of occurrence).
- Holiday starts over time (FACT, with dated code comments): until 17-Jul-2026 the 08:15 refresh also ran on weekday NSE holidays ("the token was refreshed on every NSE holiday", its S1 docstring), so the watcher could start the service on such a day and this guard refused it with exit 0 and the Telegram; from 18-Jun the watcher does not start the service again after an exit 0 dated today (section 8); from 17-Jul the refresh skips non-trading days, falling back to a weekday check on a calendar error so that a trading day is never skipped. The refresh is not scheduled at weekends. No dated record of a holiday start was found.

### 7.2 Start-window guard (FACT, main.py)
- The time comes from the time authority, a fixed UTC+05:30 offset that does not depend on the host's time zone (the function's docstring; scripts/ist_now.sh). Allowed since 25-Jul: [08:00, 18:15) IST; from 19-Jun to 25-Jul: [08:00, 16:00). Bypassed by --status, --dry-run, --interactive, --resume or TS_IGNORE_MARKET_WINDOW=1.
- Outside the window it prints "Outside service START window [08:00-18:15 IST] ... Not starting (clean exit 0) ... Token-watcher starts the service in-window after the morning token refresh" and returns 0. The line goes to the journal only: there is no Telegram, and the application log does not exist yet.
- History (RECORD-DERIVED, code comments): the guard was added on 19-Jun (FIX-189) after the 18-Jun 23:22 overnight start. Until 25-Jul one constant, 16:00, was both the start cutoff and the stop time. On 25-Jul the stop time became configurable (service_window_end, 17:35 in production) and the start cutoff was bound to the schema's exclusive bound, 18:15, so that a crash-restart between the stop time and the cutoff is not refused ("Accepted cost: the anti-overnight start window widens 16:00 -> 18:15"). The watcher kept its window (section 8).
- The exit 0 was chosen on purpose: "Outside this broad window main() exits cleanly (0) so systemd/token-watcher do not keep a long-lived process alive off-hours" (FIX-189 comment). The 25-Jul comment records one consequence, for a crash restart after the stop time: the guard "returns exit 0 — which `Restart=on-failure` does not retry — so the process stays dead for the evening". INTERPRETATION: neither comment considers a host boot before 08:00 (section 10).

### 7.3 Instance lock
- FACT (utils/instance_lock.py): two layers: an OS-owned exclusive lock (flock) on /tmp/trading-system.lock, which the docstring calls authoritative (X5, 17-Jul), and a socket bound to loopback port 5001. A refusal logs CRITICAL and returns 1, which systemd restarts after 10 seconds.
- RECORD-DERIVED (17-Jul X5 note, system map), in its context: after advising against "a standalone `main.py --resume` (it competes for instance-lock port 5001)", it says "the lock is now OS-owned (`fcntl.flock` on the lock file) as well as the port, so a standalone `main.py` is refused by BOTH layers".
- INTERPRETATION / AUDIT LEAD (not tested on a VM; not raised to fact): the repository unit sets PrivateTmp=true, and CURRENT EXTERNAL FACT (systemd.exec, checked 2026-10-09): with PrivateTmp= "/tmp/ and /var/tmp/ directories inside it are not shared with processes outside of the namespace", which "makes sharing between processes via /tmp/ or /var/tmp/ impossible". Read together, the service's lock file would sit in its private /tmp, so an instance started outside the unit (for example a standalone main.py --resume over SSH) would be refused by the port layer only, which would contradict the X5 note for that case. Two standalone processes share the host's /tmp, so the note holds for them, and the lock tests ran outside the unit (19-Jul record), where they would not meet the service's namespace. RECORD-DERIVED (19-Jul): a stale lock file from those tests sat in the host's /tmp and was judged harmless because "port 5001 free", which fits this reading without proving it. No inspected record mentions PrivateTmp. Which reading held on the VM is NOT ESTABLISHED.

### 7.5 What a start leaves behind (FACT)
- Exit 0 had three meanings: not a trading day, outside the start window, and a clean end of the session (also --status, --version and a passing --dry-run). The watcher and the liveness probe see only the exit code and the unit's state.
- A refused start writes one journal line and, on a holiday, one Telegram a day. The token gate's exit 6 writes a CRITICAL line to the application log with no alert call (the notifier is built later, as on A-009's exit-5 path) and is restarted by systemd every 10 seconds under the repository unit.
- An attempt that passes the guards writes today's session row early (A-011 section 5, step 9), so a later attempt the same day is classified CRASH, not COLD.

## 8. The token watcher in detail (FACT, deploy/token_watcher.sh; adds to A-011 sections 5 and 7)
- It loops every SLEEP_SEC (30 seconds) and skips a turn while a token copy is in progress (a .tmp file; FIX-040).
- Each turn it reads ActiveState, ExecMainStatus and ExecMainExitTimestamp with `systemctl show`, takes the date part of the exit timestamp, and compares it with today's IST date computed with `TZ=Asia/Kolkata date`.
- Its exit-code contract (header comment): "0 = clean EOD / holiday -> restart ONLY if the clean exit was a PRIOR day (today's EOD is done; don't hammer post-EOD)". Its window comment calls main.py "the authoritative backstop (it also exits 0 off-hours)". The contract does not list the start-window refusal among the meanings of exit 0 (section 10).

| Unit state | Last exit | Action |
|---|---|---|
| active or activating | any | Nothing (clears its alert flags) |
| failed | 4 (HALT) | Exited today: no start, one Telegram a day, sleep 300 s. Earlier day: start if the token is fresh and the IST hour is 08 to 15 |
| failed | 3 (start-up check) | As exit 4 |
| failed | any other code (1, 2, 5 and others) | Start if the token is fresh, the hour is 08 to 15 and fewer than 3 crash starts happened in the last hour; otherwise one Telegram a day and sleep 300 s |
| inactive | 0 dated today | Nothing: "today's session already completed cleanly -- do NOT restart post-EOD" |
| inactive | any other case (an exit on an earlier day, or no exit since the host boot: "never started this boot", its comment) | Start if the token is fresh and the hour is 08 to 15 ("Fresh token detected (daily start, in service window)") |

- Fresh token: the token file exists, its date is today in IST and its access token is not empty (a five-second check run with the shared venv's Python).
- Window: hours 08 to 15 IST, that is 08:00:00 to 15:59:59 (`[ "$h" -ge 8 ] && [ "$h" -lt 16 ]`; FIX-189, 19-Jun). Its comment calls this "(08:00-16:00 IST)" and says it "Mirrors the main.py guard"; that has been stale since 25-Jul, when main.py's cutoff moved to 18:15 (section 7.2). A-011 section 9 already records both windows.
- State: crash counts and daily alert flags in /tmp/ts_watcher_state (the watcher runs as root without PrivateTmp); its log in logs/token_watcher.log; its Telegram messages at WARNING, with no sentinel and so no email (its comment).
- History (RECORD-DERIVED): before FIX-188 (18-Jun) it restarted an exit-4 HALT every 30 seconds (known-issues entry); in April, DEPLOYMENT.md (F.1) recorded that starting the service on token arrival was "NOT implemented" and the start was manual.
- INTERPRETATION: the exit-date test compares an IST date (forced) with a timestamp that systemctl prints in the host's local zone by default (CURRENT EXTERNAL FACT, systemctl: the default format is "Day YYYY-MM-DD HH:MM:SS TZ", with a separate UTC option). It was consistent only because the host ran on IST (section 11).
