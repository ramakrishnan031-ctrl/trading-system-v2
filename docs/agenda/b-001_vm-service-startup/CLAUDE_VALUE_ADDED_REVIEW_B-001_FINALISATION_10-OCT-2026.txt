3.1 Daily process model (Q-B001-05)
Claude's preference for a fresh main process per trading session under an always-on supervisor is a reasonable candidate, not a decision. Improve the comparison:
- A fresh process resets process memory but does not guarantee clean persisted DB state.
- A long-lived process need not treat in-memory state as authoritative; persisted state can still be reconciled.
- Broker-side GTT protection is not guaranteed merely by choosing a process model. Actual protective orders and status must be verified per position.
- Include measured startup/reconciliation duration, intraday reboot with open positions, broker/API availability, duplicate-start fencing, restart recovery, alert delivery, and session-boundary tests.
- Keep DEFERRED until B-008, B-011, B-012, M-001 and O-010 have been discussed.

3.2 Host/environment preference
“One production VM + Windows development PC” is Rama's preference/raw input, not yet an approved architecture. Keep separate questions open:
- acceptability of having no separate validation VM;
- PC pre-live validation method;
- whether tests may run on production;
- deployment/rollback controls;
- static IP/provider/region;
- OS/runtime pinning.
Do not imply “the first live run of every change happens on production” has been approved.

3.3 Boot boundary
“VM boot alone never begins trading initialization” is a proposed policy, not a legacy fact or final design. Distinguish host boot from starting an always-on supervisor. A supervisor/scheduler may still need to start on host boot so it can evaluate time, token, prerequisites and recovery. Unexpected intraday reboot risks leaving open positions unmanaged until the recovery path runs. Keep the trade-off open.

3.4 Prerequisites
Separate candidate checks into:
- hard gate;
- restricted recovery gate (manage existing positions, block new entries);
- advisory health check;
- post-start readiness gate.
These are design discussion categories for B-002–B-007, B-012, M-006, I-010 and L-003. Do not retroactively claim the legacy system implemented them this way.

3.5 Security controls
For every proposed control, later specify protected asset/action, threat/actor, prevention versus detection, enforcement point, exception/approval, evidence retention, alert recipient/severity, and false-positive/recovery behavior. A YAML value does not enforce a concurrent-access limit unless a real component or OS control reads and applies it. Copy alerts are not copy prevention. Do not approve or implement these controls in B-001.

3.6 Register references
