## 2. A complete configuration inventory (RAMA B2-06; VP-68)
- RAMA (B2-06, quoted): "UNKNOWN, No complete, authoritative inventory of all configuration sources, keys, and downstream consumers is known to exist for the legacy system. While individual schemas (such as Pydantic models in core/config_loader.py and strategy definitions in strategies/loader.py) describe local keys, an end-to-end mapping across the entire system must be investigated and established from repository source tracing., So need one in new system take note of it".
- LEGACY (B-002_manual.md sections 3, 4 and 8): a service start read about twenty configuration sources, several outside config/; four readers used fixed paths that ignored --config; the environment arrived by two routes in one process; strategy files were read twice; one configuration file was first read after the system had announced itself active; the usage tracker meant to show which keys were read had read instrumentation that was not wired to consumers, so it reported all 388 registered keys as unread on 26-Aug-2026 (RECORD-DERIVED), which is not evidence that those settings were unused; three mechanisms observed configuration, and none was a complete inventory; the hand-written configuration guide and several docstrings had gone stale. A-009 section 3 was the first assembled list of configuration files, written during this project, not by the legacy system.
- CLAUDE CONSIDERATIONS (for the configuration design step; considerations, not requirements, until decided there):
  1. Scope: every configuration source a V2 process reads, per environment: configuration files, environment variables and secrets by name only, command-line flags, service-unit settings, calendars, and any broker-provided parameter cached as configuration.
  2. One entry per key: source and location; owner; format and parser; type, unit and allowed range; required or default (VP-48 already proposes no defaults for business values); the reading module and the point of the start at which it is read; whether it may change while the service runs (VP-15); the change route (VP-46); whether it is hashed, snapshotted and alerted on change; which environments use it; whether it is a secret.
  3. Generated and checked, not hand-written: produced from the schemas and the single loader's registry, so that it cannot drift from the code, and checked at every start, for example by failing the start when a declared key is never consumed or an undeclared key is read (VP-48). A generated registry describes what is declared; on its own it does not prove that the running code uses each value correctly (item 6).
  4. One loading point: every configuration source read by one loader, from one root passed explicitly, at one stage before any state is changed, so that the inventory and the running process cannot disagree (legacy: fixed-path readers, a separate holiday reader before logging, strategies read twice, a registry read after STARTUP).
  5. As evidence: a dated copy of the inventory and of the resolved values kept with each deployment and in the daily evidence (VP-46; L-008), secrets by name only.
  6. What "read" and "consumed" mean (ChatGPT's 13-Oct review, section 4): a value can be consumed by direct field access without passing any tracker, and the legacy tracker's silence was not evidence of non-use. The inventory's mechanism would therefore define both words (for example: read = obtained from the loaded configuration object; consumed = used by the code path that the key governs) and be tested against them, including a test that a deliberately unused key is reported and a used key is not.
- OPEN: the form (a machine-readable registry, a generated document, or both), the owner, the enforcement point, and the definitions of item 6. All belong to the configuration design step (build phase), with M-003 for deployment and L-008 for evidence.
