Current manual wording labels the relocation transaction spanning two files as an “INTERPRETATION / AUDIT LEAD” and says the SQLite page still needs confirmation. I opened the official SQLite WAL documentation on 14-Oct-2026:
https://www.sqlite.org/wal.html
Section “Overview” explicitly states that transactions changing multiple ATTACHed databases are atomic for each individual database, but not atomic across all databases as a set. The same page explains that WAL uses separate per-database WAL files and that a commit is recorded in the WAL.

Required action:
- Replace the “page could not be fetched / to be confirmed” note with a direct reference to the official SQLite WAL page and the specific limitation.
- Reclassify this as a SOURCE-VERIFIED SQLite behaviour plus a CODE-PATH / CONDITIONAL FAILURE WINDOW, not as a claim that data loss actually occurred.
- Keep the historical qualification: the recorded production v27→v28 relocation moved zero rows, so the inspected historical event does not establish an actual lost/misplaced-row incident.
- Explain that the migration transaction spans `main` and `analytics`; in WAL mode, SQLite does not promise atomic commit across both files as one set. A crash/failure around commit can therefore leave the files inconsistent with each other even though each individual file's transaction is atomic.
- Do not overstate the exact direction of inconsistency (duplicate vs missing rows) without proving the commit/failure sequence from code and SQLite semantics.
- Add a follow-up test/audit question for later governance: what recovery/integrity check would detect and resolve a partial cross-file relocation? This is an OPEN V2 consideration owned by K-001/K-002/K-013/N-005, not a design decision in B-003.
- The SQLite forum URL supplied by Rama could not be fetched in this review. Do not attribute a claim to that forum post unless its contents are independently read. The official SQLite documentation is sufficient for the narrow WAL atomicity point.

Suggested replacement paragraph for §6.2:

SQLite's official WAL documentation states that a transaction modifying multiple attached databases is atomic for each database individually, but not atomic across the set.
