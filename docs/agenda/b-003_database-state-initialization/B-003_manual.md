## 6. Migrations

### 6.1 Mechanism (FACT, SOURCE-VERIFIED)
- schema.sql is the only definition of every table (core/migrations.py lines 22 to 33). A rebuild takes the table's current CREATE TABLE block from schema.sql, skips the table when its live definition already matches (normalised text) or when it does not exist yet (the script will create it), and otherwise, with foreign keys switched off, runs in one BEGIN IMMEDIATE transaction: create a temporary table from the new definition, copy the columns common to both (generated columns excluded), drop the old table, rename, recreate the table's indexes, and run PRAGMA foreign_key_check on the whole database; any violation fails the rebuild (lines 254 to 331).
- MIGRATION_TABLES (lines 115 to 133) names the tables rebuilt at each version: 25 signals, trades, orders, kill_switch_state (CHECK constraints); 26 screener_results, smart_tgt_state, shadow_trades, reconciliation_log, innings (foreign keys); 27 fm_ledger, webhook_audit (a stored date column); 29, 30, 34, 35 and 45 trades; 32 trades and order_execution_log; 38 signals. Versions with no entry were pure additions, created by the script (lines 52 to 90).
- run_migrations (lines 400 to 444) visits the versions above the stored one in order and rebuilds each named table once, to its current definition; a table no longer in schema.sql is skipped. Any failure is raised as MigrationError naming the table.
- Relocation (version 28; lines 338 to 393): for each of candles, system_metrics and system_metrics_daily still present in the main database, one BEGIN IMMEDIATE transaction empties the analytics copy, copies the common columns across and drops the main table. It runs after the rebuilds and before the script. A table already absent from the main database is skipped.
- The rebuilds do not use ALTER TABLE ADD COLUMN; new columns arrive through a rebuild and take their default or NULL. New indexes come from the script or from a rebuild.

### 6.2 Atomicity (three layers: library or vendor behaviour, code path, historical outcome)
- Table rebuilds.
  - Code path (FACT, SOURCE-VERIFIED): _rebuild_table_from_schema runs each table's rebuild in one BEGIN IMMEDIATE transaction and issues ROLLBACK on any exception, a failed foreign-key check included (core/migrations.py lines 298 to 325). That bound is per table. The other tables of a version step, the relocation that follows the rebuilds and the schema script of S11 are separate transactions or autocommit statements; no transaction spans them. A migration run is therefore not atomic as a whole: if a later table fails, the tables already rebuilt stay rebuilt, the stored version stays at its old value (the stamp comes only from S11), and the next permitted start rebuilds what is left (finished tables are skipped). The comment at state_store.py lines 415 to 419 describes this outcome ("leaving the version untouched so the migration is retried on next startup").
  - Vendor behaviour (CURRENT EXTERNAL FACT, checked 2026-10-14): transactions "continue to be atomic within each individual database file" (https://www.sqlite.org/lang_attach.html).
  - Historical outcome (RECORD-DERIVED): the recorded migrations of 14-Jun, 13-Jul and 28-Jul completed (section 6.4); no record of a failed or partial migration was found (section 2's search scope).
  - Tests: the repository's rollback test covers a failure in the first table rebuilt only (section 14). The "atomic on failure" statement for version 45 is a source comment about one rehearsal on a copy of the production database (423 trades, 713 orders, 49,410 signals: 134 ms, integrity ok, no foreign-key violation; a fault injected after the drop and rename "left [the DB] at v44, un-rebuilt and undamaged", core/migrations.py lines 97 to 102), not a repository test. Neither covers a failure at a later step of a run, power loss or a killed process.
- The schema script (S11).
  - Library behaviour (LIBRARY TEST 3): with isolation_level=None, a script keeps the statements that ran before a failing one.
  - Code path (FACT, SOURCE-VERIFIED): S11 runs in autocommit mode and the version stamp is its last statement, so a failure part-way leaves the earlier statements applied and the version unchanged.
  - Historical outcome: no failed script recorded (section 2's search scope).
- The analytics relocation across two files: CONDITIONAL FAILURE WINDOW; NO OBSERVED OCCURRENCE FOUND.
  - Vendor behaviour (CURRENT EXTERNAL FACT, checked 2026-10-14): SQLite's write-ahead-logging page states, under "1. Overview": "Transactions that involve changes against multiple ATTACHed databases are atomic for each individual database, but are not atomic across all databases as a set" (https://www.sqlite.org/wal.html). Its ATTACH page states: "If the main database is ":memory:" or if the journal_mode is WAL, then transactions continue to be atomic within each individual database file. But if the host computer crashes in the middle of a COMMIT where two or more database files are updated, some of those files might get the changes where others might not" (https://www.sqlite.org/lang_attach.html). The pages describe current SQLite; the production host's SQLite version is NOT ESTABLISHED (section 4.4).
  - Code path (FACT, SOURCE-VERIFIED): relocate_analytics_tables (core/migrations.py lines 338 to 393) runs, per table, one BEGIN IMMEDIATE transaction on a connection whose main database is in WAL mode (the state store's settings) and whose attached analytics database is set to WAL (core/db_connect.py lines 38 to 41): it empties analytics.<table>, copies the rows across, drops main.<table>, and commits. That one transaction updates both files, which is the case the documentation describes: atomic in each file, not across the two.
  - What a split would leave (code path; conditional): if only the analytics side committed, the main table still exists and the next permitted start relocates it again, emptying the analytics copy first (lines 359 to 384), so the two files converge; if only the main side committed, the main table is gone without its rows in the analytics file, and the next start skips that table because it is no longer in the main database, so the code would not bring the rows back. Which of the two SQLite produces (the order in which it commits the two files), and whether a process failure, as against the host crash the documentation names, can produce a split, were not established. The docstring's "a crash mid-migration can be retried without duplicating rows" (lines 352 to 355) holds for the first case only.
  - Historical outcome (RECORD-DERIVED): the one production relocation recorded, on 14-Jun, "moved 0 rows" because the analytics tables were empty on the live database (section 6.4). No crash during it is recorded. No historical data loss or misplaced row is established.
  - Open, not decided here: what check would detect and resolve a partial cross-file move (Q-41 (h); B-003_v2_design_inputs.md section 2, item 3).
