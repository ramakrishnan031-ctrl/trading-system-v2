R2 — Distinguish broker rejection, request failure and local token metadata (HIGH)
Keep this exact sequence consistent everywhere:
1. Constructing the Kite client sends no request.
2. Start-up check 4 sends an authenticated quote request.
3. Any exception/failure caught by the clock check blocks startup with exit 3.
4. Only if that request succeeds does the later token gate inspect local metadata; that path can return exit 6.
5. A successful read does not prove order placement is authorized, including the registered-static-IP condition.

Do not write “invalid token means exit 6.” A token rejected by the broker at the clock check is the exit-3 path in this baseline. Exit 6 at BC9 is the narrower local-metadata path after the earlier broker request succeeded.

The conclusion that BC5-BC7 can leave the service down for the rest of that day is a repository-supervisor code-path conclusion, not an observed event. Keep “NO OBSERVED OCCURRENCE FOUND” and “installed host state UNKNOWN” close to it. Do not convert it into a historical incident.

R3 — Preserve the transport-failure finding as conditional, not observed (HIGH)
Keep the evidence chain in B-004_manual.md section 7.3:
- kiteconnect re-raises requests transport exceptions unchanged;
- the adapter maps NetworkException and Python TimeoutError/socket.timeout, but not requests ConnectionError/ReadTimeout;
- those client-side failures therefore reach callers as generic BrokerError, not BrokerTimeoutError;
- the placer treats BrokerTimeoutError as unknown/in-flight, but another BrokerError as a failed attempt and releases the reservation;
- if placement reached the broker before a client-side read timeout, local and broker state could diverge.

Retain the exact label: “KNOWN DEFECT — CONDITIONAL CODE PATH / LATENT; NO OBSERVED OCCURRENCE FOUND.” Do not claim an actual naked position, lost order or historical loss. The localhost test establishes exception classes, not historical production occurrence. Existing tests demonstrate a test gap, not proof the defect happened. Downstream G/I owners should cite section 7.3 rather than reproduce a different version.

R5 — Preserve configured versus effective timeout (HIGH)

Identify library behaviour as LIBRARY SOURCE and the resulting application path as source evidence plus that dependency. requirements.txt pins versions; it does not prove which packages were installed on a historical host.
