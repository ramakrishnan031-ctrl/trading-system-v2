## 5. What "worker initialization" meant in the legacy (FACT unless marked)
- Construction: in Phase 0e. A constructor could already start a thread (TH4) or create a pool (TH22), and several workers were started in Phase 0e itself (ST2, ST4).
- Start: one call per worker, returning at once (section 4).
- Connect: only the feed connected to anything at start (TH15, WebSocket). Every other worker reached the broker per call through the adapter (B-004 sections 3 and 8). The feed's only connection state is the _connected flag, set by the library's on_connect callback and cleared on close or give-up (live_feed.py 337, 368, 440).
- Subscribe: only LiveFeedManager.subscribe() (live_feed.py 173 to 197). Its only caller in the runtime files is the order placer's exit retry (orders/order_placer.py 3404, FIX-061); nothing subscribes at start, and the connect handler returns at once when nothing is tracked (live_feed.py 340 to 343). B-004 section 10 records the 25-Jul measurement (32 connections, no instrument subscribed, no tick).
- Ready: no worker reported readiness and no start step tested one. The end of the start is marked by the STARTUP event and the "System Active" Telegram (ST10); what counted as ready is B-007's.
- RAMA (EXPECTED) B6-03 and B6-11 (a phased boundary ending in connected and subscribed workers, with "subscribed" and "receiving data" as separate tracked states) do not match: there was no subscription at start and no subscribed or receiving state beyond the tracked set and the last-tick time (live_feed.py 82, 119).

## 6. The market-data feed as a worker (adds to B-004 section 10; FACT unless marked)
- In live mode connect() starts TH13, starts TH14, builds the ticker with 10 reconnect tries and a 5-second maximum delay (constructor defaults, live_feed.py 45 to 46 and 510 to 524) and starts it in its own thread (TH15). In paper mode it logs and returns (138 to 140).
- Ticks would go from the library's thread to a queue of 10,000 (36, 89), and TH13 would hand validated batches to the registered callbacks (526 to 620). main.py registers one dispatcher that feeds the candle store and the shadow tracker (2963 to 2971); the candle store's close callbacks are the candle writer (3926 to 3944) and smart target's trail (smart_tgt_manager.py 150 to 151, 171). Callbacks are held by weak reference (live_feed.py 85 to 87, 211 to 232).
- TH12 fires on every 60-second boundary whether or not a tick arrived (candle_store.py 233 to 251); with no tick for any token there is nothing to close. RECORD-DERIVED (25-Jul-2026, memory/dormant_tick_candle_path_25jul.md lines 47 to 49, 57 to 59, 70 to 77 and 82 to 89): the feed "has connected 32 times and never carried a single token"; the candle writer wrote no row; smart target's trail never fired, for this reason and for an independent one (no trade was ever registered with it, smart_tgt_state empty); the tick-age watchdog never armed; and FIX-029's consumer-thread check, then placed after the arming loop, "has never run in production" until it was moved ahead of the arming check on 25-Jul (live_feed.py 708 to 729). The record calls the dormancy a decision with a reopen trigger (lines 14 to 34).
- Failure handling inside the feed: a full queue would call the kill switch only if one was passed (302 to 322); main.py passes none (2927 to 2938), so it would only log and drop the tick (317 to 322; A-011 section 8 lists these calls as inert). A gap over 10 minutes, reconnects exhausted inside market hours, and the watchdog go through main.py's critical-failure callback, which sets SOFT_KILL and sends a Telegram (live_feed.py 416 to 424, 472 to 480, 772 to 782; main.py 657 to 685; A-011 section 8). Exhaustion outside market hours is a WARNING only (449 to 470, B-004 section 10).
- Settings not wired: the configuration's live_feed section (config/system_config.yaml lines 743 to 746, max_reconnect_attempts 10, backoff 1 to 30 s) and its schema class (core/config_loader.py lines 1819 to 1821) are read by no runtime file found in the search; main.py passes no reconnect values, so the constructor defaults apply. set_notifier() (live_feed.py 250 to 253) has no caller in the runtime files searched, so on the code path the feed's own reconnect and off-hours Telegrams (395 to 408, 456 to 469) had no notifier to send through; its "WebSocket DEAD" alert goes through send_alert_recorded with no notifier (494 to 504). ## 8. What held the process open at exit (authoritative for B-006; rows X1 to X5)
- X1, LIBRARY SOURCE (CPython 3.12.3): at interpreter exit, threading's shutdown first runs the executor exit hook, which tells every ThreadPoolExecutor worker to stop and joins it after its current and queued work (concurrent/futures/thread.py lines 23 to 37), whatever its daemon flag; it then joins the non-daemon threads; daemon threads are not joined. A pool's thread is created by the thread that submits work and inherits that thread's daemon flag (thread.py 197 to 202).
- X2, LIBRARY TEST (2026-10-19; Python 3.12.3 and 3.13.16; scratch script, no legacy code): a process that called sys.exit(2) while a 2-second pool task ran (submitted from a daemon thread) and two daemon threads slept for 60 seconds ended after 2.0 seconds with status 2. A pool worker created from a daemon thread reported daemon=True; one created from the main thread, daemon=False.
- X3, code path: every named worker thread of section 3 is a daemon thread except the HARD_KILL flatten worker (TH31). The pools of TH20, TH21 and TH22 are fed from daemon threads (the dispatcher, the gate's poll, the candle timer). INTERPRETATION: the event-bus async workers (TH31) take the flag of the thread that first published an OrderFilled or PositionClosed event, which could be the main thread during PASS 1.
- X4, INTERPRETATION of the code path with X1 and X2 (not a measured duration on a host): after a late exit (F2, F3, F4, F7) the process ended once the main thread returned and the pools had finished their current and queued tasks, and, if a HARD_KILL flatten was running, once it finished. The daemon workers, including the order monitor, the reconciler, the MIS and EOD pollers and the webhook server, were stopped by the interpreter without their stop methods; _shutdown did not run, so there was no entry-order cancel, no SHUTDOWN event, no WAL checkpoint and no "System Stopping" Telegram. On F2 and F3 the store was closed first while TH1 to TH5 and TH7 to TH10 were still running. B-002's open point ("whether it exits at once depends on its worker threads") is answered for the code path: it exits within the time its pools and any flatten need; occurrence is NOT ESTABLISHED (section 20).
- X5, the normal stop: a signal or the self-exit gate sets the shutdown event; _shutdown stops the workers in A-011 section 11's order (section 9) and main returns 0. The repository unit waits 30 seconds after SIGINT before killing (B-001 section 5; A-011 section 11).

## 23. Final B-006 statement
At the baseline the trading service was one Python process whose main thread built every component and started its workers in two waves: nine threads during construction, before the startup reconcile and before the last gates that could end the start (among them the MIS auto square-off poller), and the rest after it. No step of the inspected start path waited for a worker to be ready; the only connection at start, the feed's WebSocket, carried no subscription. Every named worker was a daemon thread except the HARD_KILL flatten worker, so, on the code path, a start that ended late left no teardown: the process ended when its pools and any flatten finished, without the workers' stop methods (occurrence not established). Worker loops caught their own exceptions and kept running, which hid one recorded failure for two days (F12); the order monitor alone stopped itself after repeated broker failures. These are legacy facts for B-007 to B-012, not V2 requirements.
