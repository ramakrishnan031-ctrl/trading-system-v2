## 3. What "ready" meant in the legacy (FACT unless marked)
- The trading service had no readiness state. A-011 sections 3 and 4 record that no state named READY exists in the service's code; B-006 section 4 records that no start step waited for a worker to report that it was running, connected or healthy. B-007 confirms both for the inspected path. In the INSPECTED SCOPE no component in the trading path (signals/, screening/, orders/, capital/, broker/, strategies/, core/ and main.py) was found to read a readiness or health value before taking an entry: no reader of the feed's connection flag, the tick age, a worker's liveness method or /health was found there, other than the liveness methods' own definitions and the health server's providers. The kill switch's in-memory state is read on the entry path (A-011 section 8.1), and specific failure paths set it (section 10).
- The end of a start was a sequence, not a verdict: the STARTUP event (main.py lines 4168 to 4173), the session row written again (4174 to 4180), an INFO Telegram "System Active" (account, capital, market OPEN or CLOSED, time; 4191 to 4201) and the log line "All subsystems started -- entering runtime loop" (4205; B-006 ST10). The message carries no health content. On the code path it is sent also when the webhook self-check has just failed and the start continued DEGRADED (G16): main.py reads the self-check's result only at lines 4005, 4006 and 4050, inside the self-check block; no recorded occurrence of a DEGRADED start was found.
- The word READY appears outside the service in two places, each computed by another process and gating nothing: the pre-flight's overall verdict (READY, READY_WITH_WARNINGS or CRITICAL_FAILURE; section 7) and the GUI's System Health label (READY, NOT READY or NOT CONFIRMED; section 8). The interactive start's "[OK] System ready for signals" (main.py line 4213) was not reachable at the baseline (B-002 M27). A-011 section 4 said READY appears "only as the pre-flight verdict ... that the GUI shows"; erratum A-011 E-7 corrects it (section 21; accepted, DR-044).
- RECORD-DERIVED (21-Jun-2026, memory/preflight_system_21jun.md lines 13 to 18; the same words in docs/SYSTEM_MAP.md line 1565): the pre-flight was "ALERT-ONLY (exit 0 always; Rama is the gate, never auto-blocks)". RECORD-DERIVED (20-Jul-2026, memory/monday_first_real_boot_20jul.md lines 11 to 18): on the first production start after the 17-Jul outage, a read-only "boot-window check" at 09:04 IST covered six items (the token file, the unit's state, the start log, the liveness log, the broker session, the webhook listener). INTERPRETATION: readiness in practice was the operator's judgement over such reports; how often such checks were made is NOT ESTABLISHED.

### 3.1 Walkthrough of a live daily start (navigation aid; the rows cited are authoritative)
1. Service start and the guards before logging. On the recorded days the token watcher started the unit after the 08:15 token refresh (B-001 section 6; RECORD-DERIVED 05-Aug and 26-Aug). G1: the holiday guard, on the host-local date (main.py lines 2098 to 2152; utils/holiday_guard.py lines 85 to 95), returns 0 on a weekend or a listed holiday and passes a missing holiday file, which then ends the start at G3 with exit 5 (B-002 M1); the service-window guard follows (line 2154 onward), bypassed for --status, --dry-run, --interactive, --resume or TS_IGNORE_MARKET_WINDOW=1 (lines 2155 to 2160). G2: the instance lock.
2. Configuration and state: G3 (exit 5) and G4 (the database opened, migrated or created).
3. Scenario and session row: G5 ends a HALT start with exit 4; G6 writes today's session row, before every later gate.
4. The live pre-load (G7) and the start-up checks (G8; section 5): one report; a blocking failure ends the start with exit 3; warnings go to one INFO line.
5. Token, broker, capital and kill-switch gates (G9 to G13).
6. Construction and the first workers (B-006 ST1 to ST4): TH1 to TH4 and the optional workers start; the configuration gates (G14) and the kill check after PASS 1 (G15) can still end the start, with workers running.
7. The feed and the remaining workers (B-006 ST7 and ST8): no step waits for a connection, a subscription or a first tick (section 9).
8. The webhook receiver (TH24), a 2-second sleep, the webhook self-check (G16; since 27-Jul a failure DEGRADES and the start goes on), then the health server (H1, TH25). The health server's start is not a readiness verdict: it follows a DEGRADED self-check as well, and /health has no webhook entry, so it can answer healthy then (section 6).
9. The end of the start (B-006 ST10): the configuration-access check (main.py line 4164), the STARTUP event, the session row written again, "System Active" and "All subsystems started -- entering runtime loop"; then the composition check (G17), which in live only logs and alerts; then the main thread waits for shutdown.
10. Run time: in the inspected path a health condition changes trading permission through a kill-switch call on its own failure path (section 10), for example the feed's 10-minute gap or exhausted reconnects inside market hours (SOFT_KILL through main.py's callback, section 9) or three consecutive order-monitor failures (HARD_KILL, B-006 F9); other conditions are reported (sections 6 and 12).
- In parallel, on their own schedules, with no step above waiting for them: the pre-flight's Phases A (08:30), B (09:14) and C (09:15 to about 09:20), Phase B reading /health and /metrics and Phase C /metrics and the webhook /health (section 7); the GUI's backend, which reads /health and the pre-flight tables (section 8); the liveness probe every 5 minutes from 09:00 to 15:55, reading the unit's state and the database's kill row (section 11); the cron watchdog at 19:30 (section 11). After a restart in [06:00, 09:20), main.py launches a missed pre-flight phase as a child process (TH30; section 7).
- Unresolved sequencing: Phase A against the start (RECORD-DERIVED: the unit active at 08:15:05 on 05-Aug, B-001 section 6, and "All subsystems started" at 08:15:36 on 20-Jul, memory/monday_first_real_boot_20jul.md line 15, so on those days the service was running before 08:30, and on 20-Jul its start had ended; on other days NOT ESTABLISHED; section 7); when anyone first read /health on a given day; which steps the 10-Aug start passed (section 4).
