The two-system plan can be read as consistent if DR-028 applies per system, but as a scope expansion if it applies to V2 as a whole. Do not silently choose either reading or edit DR-028. A new register decision must explicitly settle this scope question; Claude recommends placing it in the Section C end-decision paper rather than treating it as a C-002 transport fact. That is a reasonable scheduling recommendation, but Rama owns the decision.

The technical boundary already supported by C-002 is:
- Each Chartink alert has one configured webhook URL.
- The URL path selects the legacy receiver’s scanner key.
- A display-name prefix is not the transport route and cannot by itself route an HTTP request to the other VM.
- Therefore, for two VMs, each alert must be configured to send to the intended system’s endpoint; the naming prefix can help human identification and may support a validation rule, but it does not replace endpoint isolation.
- One Chartink account is a shared external dependency. If Chartink or that account is unavailable, both systems may lose their common signal source. Independent VMs do not remove that shared dependency.

V2 questions to carry forward, without deciding them now:
1. Is DR-028 scoped per system or across the entire V2 deployment?
2. Are client codes necessary in human-readable scan names, or should a non-sensitive stable system alias be used?
3. What is the authoritative system identity: endpoint/path namespace, configuration mapping, payload check, or multiple checks?
4. How should a system reject a scanner name/payload that indicates the other system?
5. Must each system have separate webhook secrets and other credentials? VP-56 already proposes per-environment separation; per-system isolation must be explicitly considered.
6. How will external scan names map to immutable internal strategy IDs and YAML/config entries?
7. How are renames, duplicate names, case, separators and migrations handled?
8. Can the Chartink subscription support the required number of alerts? This remains U-10.
9. How will a common Chartink outage be detected and handled across both systems?

Security recommendation for review: embedding the actual broker client code in scan names causes it to appear in the scan_name field and potentially in payloads/logs unless redacted or mapped. This is not a prohibition or a final decision; it is a privacy/security consideration for VP-45. A non-sensitive alias is an option to evaluate with Rama.
