5. ADDITIONAL USER INPUT: TWO SYSTEMS / TWO VMs USING CHARTINK

The user’s proposed operational need is to distinguish alerts belonging to two separate systems while using the same Chartink account/site. One possible naming convention is to put a broker client code before the strategy name. This is a useful requirement to record, but it is a V2 design question and must not be silently decided during the legacy-documentation phase.

Important legacy facts from C-002:
- The legacy receiver’s path key was an exact, case-sensitive scanner-map key.
- The configured key had to match the scanner name/path segment expected by the receiver.
- The legacy payload could include scan_name and alert_name, but the receiver’s primary routing identity was the URL path segment; body metadata was not a substitute for the route key.
- The legacy repository did not prove what scanner names or webhook URLs were actually saved in Chartink.
- The legacy design used a shared token in a query parameter and plain HTTP. These are historical facts, not a pattern to carry forward.

For later V2 governance, explicitly resolve the following questions before freezing a naming contract:
1. Is the external scanner/alert name required to be globally unique across both systems, or only unique within each system?
2. Which identifier is authoritative for system/tenant routing: a path namespace, a separately configured endpoint, an explicit system identifier, or a combination?
3. How is the external Chartink scanner name mapped to an internal strategy ID? The external display name should not be assumed to be the internal strategy/config key.
4. What happens if the path says System A but the payload says System B, or if the scanner name is unknown or mismatched?
5. Are endpoints and authentication credentials isolated per system/VM? Avoid shared credentials across systems where independent isolation is required.
6. How are strategy renames, duplicate names, case changes, whitespace, hyphens and migration/version changes handled?
7. Is the broker client code actually needed for routing? Prefer a non-sensitive, stable system alias over embedding a real broker client identifier in scanner names, logs, payloads or filenames. Client identifiers should not be exposed merely for convenience.
8. How are historical events attributed if a scanner is renamed or moved between systems?

Illustrative naming only—not a decision:
- External display name: `<SYSTEM_ALIAS>-<STRATEGY_ALIAS>`
- Internal mapping: exact external scanner identifier → system alias + immutable strategy ID
- Routing/authorization: independently validated system identity, not inferred from a human-readable name alone

The system alias should be non-sensitive and stable. This illustration is not approval of a V2 endpoint, URL shape, authentication method, payload schema, or YAML layout. The detailed contract belongs in the later V2 design/governance phase, after Section C legacy manuals establish the facts.
