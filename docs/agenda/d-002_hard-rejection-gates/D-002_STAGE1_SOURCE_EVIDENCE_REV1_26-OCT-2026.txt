0. FINDINGS IN BRIEF (details and citations in the sections below)
========================================================================================================================
- The legacy hard gate is one module, screening/hard_gate.py: a battery, HardGate.evaluate, of three checks in a fixed
  order - at-circuit, circuit proximity, freshness (60 s) - with liquidity a no-op, returning a GateVerdict (passed,
  reason, evidence) (HG-02, HG-04); a shared circuit-proximity function (HG-03); scoring helpers; and five playbook
  gates for the V3 chain (HG-05, HG-06).
- Where it can refuse. When the HardGate enforce branch is not taken, screen() invokes the circuit-proximity check at
  step 1b. It rejects only if circuit_proximity_reason returns a reason. The function can fail open - for example, when
  disabled, when entry data is missing, or when neither usable circuit band is available. Under the recorded repository
  configuration the flag is true, so this path can reject when the function's price/band conditions are met. Repository
  configuration is not proof of deployed or runtime state. (HG-03, SC-04, WS-03; a reason gives
  REJECTED_CIRCUIT_PROXIMITY, before the step pipeline.) The HardGate battery refuses only on the enforce branch,
  REJECTED_<reason> (SC-03), and in shadow is computed and logged after scoring without effect (SC-05). The repository
  mode is shadow (WS-02), so on the repository configuration the battery logs only, and the circuit-proximity rule is
  the only hard_gate.py logic that can refuse on the screener's path (WS-04).
- Hand-off: screen() returns a ScreeningResult and writes the status; the processor stops on SKIPPED_ or a rejection and
  goes on to price derivation on PASSED (SC-07). Downstream refusals (step errors, the minimum score, the signal-age
  check) stay with D-003, D-017 and D-018 (SC-08, BD-01 to BD-04).
- Eligibility: in the authorised files the only eligibility-type refusal is the MIS learned-blocklist pre-drop, logging
  only on the repository values and owned elsewhere (EL-01); the F&O ban list is fetched and stored with no consumer in
  the authorised files (EL-03); the index universe is regime data, not eligibility (EL-04).
- Windows: neither the hard gate nor the screener checks an entry window (WN-01); the pipeline's window refusals are the
  processor's, before screen(), mapped by D-001 (WN-02).
- V3 and PB01: the playbook gates are called by v3_chain/runner.py and the PB01 entry and runner as log-only or would-be
  verdicts by their comments; none of these calls HardGate.evaluate or the circuit-proximity function (VC-01 to VC-05).
