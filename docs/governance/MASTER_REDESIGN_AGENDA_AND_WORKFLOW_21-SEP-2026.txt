======================================================================
PART 1 — AGREED REDESIGN METHODOLOGY
======================================================================

OBJECTIVE

Before redesigning or implementing anything, completely understand the
current Production system again and settle every important system decision
in an orderly manner.

We will NOT make random discussions by jumping between modules, files,
functions, S&R, entry logic, capital, orders, etc.

The agreed process is:

CURRENT SYSTEM
     ↓
MASTER REDESIGN AGENDA
     ↓
TOPIC 1
  Understand current behavior
  ↓
  Discuss KEEP / MODIFY / CHANGE / REMOVE / MERGE / SHADOW / REPLACE
  ↓
  Final decision
  ↓
  Record decision
  ↓
  Topic CLOSED / FROZEN
     ↓
TOPIC 2
     ↓
     ...
     ↓
LAST TOPIC
     ↓
COMPLETE DECISION SET
     ↓
NEW ARCHITECTURE
     ↓
DETAILED DESIGN
     ↓
IMPLEMENTATION
     ↓
TESTING
     ↓
VALIDATION
     ↓
DEPLOYMENT

IMPORTANT:

The redesign does NOT start until the complete agenda has been discussed
and all required decisions have been settled.

======================================================================
PART 2 — HOW WE WILL STUDY THE CURRENT SYSTEM
======================================================================

The agenda should NOT be purely module-wise.

It should also NOT be purely function-wise.

The primary structure will be:

    SYSTEM LIFECYCLE + DECISION DOMAIN

with module/class/function mapping underneath each topic.

Reason:

A purely function-by-function review can understand code very deeply but
can lose the business/system flow.

A purely module-by-module review can understand components but can miss
how a complete trade actually moves through the system.

Therefore every agenda topic will connect:

    SYSTEM RESPONSIBILITY
        ↓
    MODULE
        ↓
    CLASS
        ↓
    FUNCTION
        ↓
    INPUT
        ↓
    DECISION
        ↓
    OUTPUT
        ↓
    STATE CHANGE
        ↓
    DEPENDENCIES
        ↓
    FAILURE / REJECTION
        ↓
    FUTURE DECISION

This gives both complete system understanding and code-level coverage.

======================================================================
PART 3 — STANDARD DISCUSSION TEMPLATE FOR EVERY TOPIC
======================================================================

Every agenda topic should be handled using the same structure.

TOPIC: <topic name>

1. CURRENT SYSTEM
   What does Production currently do?

2. CODE / MODULES
   Which files/classes/functions implement it?

3. INPUTS
   What information enters this stage?

4. PROCESS
   What exactly happens, step by step?

5. OUTPUT
   What does the stage produce?

6. STATE CHANGE
   What is persisted or changed?

7. DEPENDENCIES
   Which other components does it depend upon?

8. PROBLEMS / LIMITATIONS
   What known problems, duplication, coupling, ambiguity or risk exist?

9. REDESIGN OPTIONS
   What could be retained, modified, replaced, merged, removed or shadowed?

10. DISCUSSION
    Discuss the alternatives and consequences.

11. FINAL DECISION
    One of:
      KEEP
      MODIFY
      CHANGE
      REMOVE
      MERGE
      SHADOW
      REPLACE

12. GOVERNANCE
    Record the decision in the project-side decision register.

13. STATUS
    CLOSED / FROZEN

A closed topic should not be casually reopened.

If a later dependency genuinely requires reopening:

    REOPENED
    Reason:
    Impact:
    New decision:
    Approval/status:

======================================================================
PART 4 — THREE CONTROL DOCUMENTS / REGISTERS
======================================================================

The redesign process should maintain three separate control records.

1. MASTER REDESIGN AGENDA

Purpose:
    Defines everything that must be studied and settled.

It prevents random discussion and missed topics.

2. DECISION REGISTER

Purpose:
    Records final decisions permanently.

Example:

    A-047 — Entry Price
    Status: CLOSED
    Decision: <final decision>
    Reason: <reason>
    Affected modules: <modules>
    Dependencies: <dependencies>

3. OPEN QUESTIONS / DEPENDENCIES REGISTER

Purpose:
    Records questions that cannot yet be decided because another topic
    must be settled first.

Example:

    Topic A-020
        ↓
    Depends on A-080
        ↓
    Mark BLOCKED
        ↓
    Continue A-021
        ↓
    Return to A-020 after A-080 is settled

This prevents one unresolved dependency from derailing the entire agenda.

Modules and functions are NOT ignored.

    Repository location

    File

        ↓

        ↓

======================================================================
PART 7 — DECISION DISCIPLINE
======================================================================

Every discussion must end with one of these outcomes:

KEEP
    Existing behavior remains substantially unchanged.

MODIFY
    Existing behavior remains but implementation/parameters/logic change.

CHANGE
    The existing business rule changes.

REMOVE
    Existing behavior is no longer required.

MERGE
    Multiple existing mechanisms become one controlled mechanism.

SHADOW
    Mechanism remains observational and does not control live decisions.

REPLACE
    Existing mechanism is replaced by a new design.

DEFER
    Decision cannot yet be made because a dependency remains unresolved.

A topic marked CLOSED is considered frozen for the redesign unless
explicitly reopened.

PART 10 — KEY PRINCIPLE
======================================================================

The redesign should NOT be:

    "Look at old code -> immediately rewrite it."

It should be:

    "Understand old system completely
     -> identify what it actually does
     -> identify what should remain
     -> identify what must change
     -> settle every decision
     -> design the new system
     -> implement only the approved design."

Therefore the answer to the central planning question is:

YES — the entire existing system should be covered again before the
whole redesign is planned.

But the coverage should be structured through the Master Redesign
Agenda, not through random module/function discussions.

The final objective is:

    CURRENT SYSTEM FULLY UNDERSTOOD
              +
    ALL REDESIGN DECISIONS SETTLED
              ↓
       NEW ARCHITECTURE
              ↓
        IMPLEMENTATION
              ↓
           TESTING
              ↓
         VALIDATION
              ↓
         PRODUCTION

END OF MASTER REDESIGN AGENDA
