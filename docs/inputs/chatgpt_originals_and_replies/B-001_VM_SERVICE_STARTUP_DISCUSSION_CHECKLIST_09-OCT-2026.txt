2.1 Main service entry and systemd unit

Production:
- Entry point: main.py.
- deploy/systemd/trading-system.service runs the virtual-environment
  Python interpreter against main.py with --mode live.
- Unit directives include Type=simple, User=ubuntu, Group=ubuntu,
  WorkingDirectory=/home/ubuntu/systems/trading-system,
  EnvironmentFile pointing to that installation's .env,
  StandardInput=null, KillSignal=SIGINT, TimeoutStopSec=30,
  Restart=on-failure, RestartSec=10, and
  RestartPreventExitStatus=3 4 5.
- The service unit specifies behavior; it does not prove the historical
  installed unit was identical at every moment.

main.py source records these process exit meanings:
- 0: clean shutdown or holiday/weekend (not started)
- 1: TradingSystemError
- 2: unexpected exception
- 3: blocking startup-check failure
- 4: HALT scenario without --resume
- 5: invalid arguments/configuration/missing environment value
- 6: token missing or expired in non-interactive live startup
- 7: live-mode confirmation cancelled
- 8: account selection cancelled

main.py startup outline, from the inspected source:
1. Parse command-line arguments.
2. Run a holiday/weekend guard before normal logger setup.
3. Apply a service-start-window guard, with explicit diagnostic/emergency
   bypass conditions in source.
4. Set up logging and acquire a single-instance lock.
5. Load validated configuration.
6. Initialize persisted state and the kill-switch/time components.
7. Detect the legacy startup scenario (COLD/WARM/CRASH/HALT) and apply
   startup checks and subsequent initialization.
The later stages belong to B-002 through B-007 and must be documented
under those topics rather than treated as fully covered by B-001.

2.2 A separate token watcher exists

Production:
- deploy/systemd/token-watcher.service runs
  /home/ubuntu/systems/trading-system/deploy/token_watcher.sh through bash.
- The unit runs as root, sets PROJECT_DIR and SLEEP_SEC=30, and has
  Restart=always with RestartSec=10.
- The script describes a polling loop that can start/restart
  trading-system.service only when its conditions are met. It reads the
  main service state and last exit status, checks token freshness and a
  time window, and distinguishes clean exit, HALT, startup failure and
  crash cases.
- The token watcher's detailed behavior is an interface to B-001, but
  token creation/refresh itself is owned by M-005 and detailed recovery
  policy by B-012.

2.3 Cron also contains startup-adjacent jobs

The generated Production crontab includes token cleanup, token refresh
and startup pre-flight jobs. The token refresh entry is scheduled at
08:15 IST Monday-Friday in deploy/cron/trading-system.cron and in the
captured sandbox crontab. The module header in
scripts/auto_refresh_token.py describes an 08:00 run. This is a source
wording/schedule discrepancy to carry to M-002/M-005; do not silently
choose one time in B-001.

Cron and systemd are separate mechanisms. Their exact division of
responsibility, actual historical enablement, and whether a given run
occurred must not be inferred only from the existence of files.

2.4 Sandbox captured unit is notable

The captured sandbox file _machine/systemd/trading-system.service.txt
also shows ExecStart invoking main.py --mode live. It additionally shows
a Wants=trading-watchman.service drop-in. The captured watchman unit says
it is bound to the main service via BindsTo and runs a monitoring script.

This is evidence of the captured unit text, NOT proof that the sandbox
traded live or that the service was actually running. Please answer the
specific historical question below if you know.

2.5 Time windows need careful boundaries

main.py and deploy/token_watcher.sh contain service-start-window guards.
The inspected main.py source defines a broad start window of 08:00 to
18:15 IST, while the token-watcher script's own comment/function describes
08:00 to 16:00 IST. The systemd restart policy and other scheduler entries
also affect when a process can be retried.

This inconsistency is a source-backed audit lead, not a V2 decision.
Detailed time-of-day/day-boundary rules are owned by B-008/B-009,
shutdown by B-011, restart/recovery by B-012, and systemd/cron by M-001/
M-002. B-001 should record the discrepancy and its ownership.
