B4-07. What happened if the client could be constructed but the first real API call failed? Did startup abort, continue partially, retry, alert, or defer the failure until a later operation?
Answer: (as below)
* The system followed a strict fail-fast principle during the startup sequence.   

* If the broker client object was instantiated but the initial connectivity/authentication probe call failed (e.g., throwing a TokenException, GeneralException, NetworkException, or HTTP 403/500 from Kite Connect):
1. Startup Aborted Immediately: It did not continue partially, run in a degraded mode, or defer the failure until the strategy attempted to place its first order. Running trading loops without a verified broker session violated safety constraints.
2. Exception Raised & Logged: The exception bubbled out of broker/zerodha_adapter.py into main.py, which logged a fatal error with the failure reason (e.g., "Broker connection/auth failed").
3. Process Exit: The main process terminated with a non-zero exit code (sys.exit(1)), halting before worker threads, ticker connections, or market-data ingestion could start.
4. Alerts: An error log entry was generated, and depending on whether notification handlers were initialized before the adapter, an alert/webhook was dispatched before process exit.
5. Retries: For authentication errors (invalid/expired token), the system did not enter an infinite retry loop; it aborted to allow an operator or auth script to supply a fresh token. For transient network errors, it may have attempted a limited number of immediate retries with backoff before aborting, but it never proceeded without a clean response
