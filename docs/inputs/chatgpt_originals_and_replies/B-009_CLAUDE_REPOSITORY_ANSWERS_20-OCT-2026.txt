F. ERRORS, DEGRADATION AND RECOVERY

B9-F1. Broker API timeout, error, rate limit or authentication failure
FACT (SOURCE-VERIFIED), by site:
- Order monitor:
  - a timeout skips the order this cycle (655-662);
  - another error counts up to 3, then HARD_KILL and the monitor STOPS ITSELF (663-689);
  - authentication failing 3 times calls the same callback and stops the monitor (640-654).
  - After it stops, nothing polls fills for the rest of the process life. See section 5, D3.
- Placement:
  - a timeout gives TIMEOUT / UNKNOWN_IN_FLIGHT with no retry (signal_processor.py 1464-1484);
  - a client rate limit re-queues up to 3 times (1486-1532);
  - other broker errors give PLACEMENT_FAILED;

5. KNOWN DEFECTS (source evidence; runtime effect not measured)
======================================================================

D1. KNOWN DEFECT — the pullback gate is wired but never fed.
- Six enabled strategies set pullback_wait_enabled: true: first_pullback_long and _short, open_high_breakdown_short, open_low_breakout_long, vwap_bounce_long, vwap_rejection_short (lines 35 or 36 of each file).
- The processor only uses the flag to skip the fresh-quote re-anchor (signal_processor.py 1082). No code path adds these signals to EntryGate (section 4).
- So, on the source path, these strategies place at once, on the stale webhook-trigger basis, with no pullback wait.
- INTERPRETATION: the gate's own 5 s poll and 2 workers run on an empty watchlist, apart from rows rehydrated from the store (entry_gate.py 195-235).

D2. KNOWN DEFECT — the per-strategy order protocol is not honoured.
- All 15 enabled intraday strategies declare CO_PLUS_TGT; the three delivery strategies declare LIMIT_TRIPLE.
- OrderPlacer always uses self._default_protocol (order_placer.py 961), whose constructor default is "LIMIT_TRIPLE" (572). main.py's construction (3061-3087) passes no protocol, and no runtime code reads the strategy's order_protocol.
- Effect on the source path: every entry is a LIMIT entry with SL and TGT placed at fill. The smart-target trail and CO-specific logic, which branch on "CO_PLUS_TGT" (order_placer.py 1881-1889, 2071-2079), never apply.
- Consistent with B-006 TH22 (RECORD-DERIVED: smart TGT never fired) and with the 03-Sep record's separate SL and TGT orders.
- INTERPRETATION: whether LIMIT_TRIPLE was intended operationally is a G-topic question; the configuration says otherwise.

D3. KNOWN DEFECT (design consequence) — the order monitor stops itself for the rest of the process.
- After 3 consecutive authentication or API failures it fires HARD_KILL and sets its own stop event (order_monitor.py 648-653, 677-688).
- No restart path was found. Fills of resting SL and TGT legs would then be seen only through the reconciler's CHECK1 or CHECK4.
- Its death is visible on /health (main.py 4067), which nothing in the trading path consumes (B-007).
