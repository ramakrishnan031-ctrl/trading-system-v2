B10-A4. What triggers EOD (FACT, SOURCE-VERIFIED)

B10-B4. Late start, double call, exception (FACT, SOURCE-VERIFIED)
- Late start: check_and_fire fires at the first poll at or after 15:17. Nothing stops a late fire on the same date: there is no upper bound in check_and_fire, unlike the recovery path's 15:30 limit.
- Double call: an in-memory per-date flag under a lock (220-227) prevents a second scheduled fire in the same process.
- Exception: the flag is reset and the exception re-raised (229-235); the poll loop retries every 5 s.
  - INTERPRETATION: an exception after reset_daily_pnl (step 7) but before return would repeat the reset on retry. The steps after it (resume, summary, telemetry) each catch their own exceptions, so this is unlikely in source terms.
- One unguarded call: get_pending_intraday_orders (873) and get_open_intraday_positions (1063) are not wrapped. A store exception there propagates out of _fire after the write-ahead row and the SOFT_KILL. The soft-kill resume (536-544) is then skipped and the next poll retries the whole sequence.
- The flag is in memory only; restart behaviour is E4.

B10-B5. Holidays, weekends, special sessions
- FACT (SOURCE-VERIFIED):
  - EOD does not fire on a holiday or weekend (217-218; market_windows.py 93-106), except on a configured special-session date.
  - The MIS unit's holiday guard is the same function (main.py 3365; mis_autosquareoff.py 330-331). But its CHECK_1, CHECK_2 and cutoff are fixed config times built once (main.py 3329-3337); they ignore special_sessions.
  - Likewise the global entry window and eod_entry_cutoff (market_windows.py 143-150, 177-190) and the order monitor's 15:15 force-close (config 740) are fixed times that ignore special sessions.
- INTERPRETATION: on a special session (for example an evening session), the MIS passes, 15:15 controls and entry window would act at their ordinary clock times, while EOD would use the session's eod_squareoff_time.
- UNKNOWN / NOT ESTABLISHED: any actual special-session run. special_sessions is empty at the baseline, and no test combining a special session with the MIS unit was found among the tests read (companion file).

B10-C2. Entry blocking during EOD (FACT, SOURCE-VERIFIED)
- EOD sets SOFT_KILL only if is_active("any") is false (382-387).
- On an ordinary day, if the order monitor ran its 15:15 force-close, SOFT_KILL is already active at 15:17. EOD then sets nothing and resumes nothing (388-392, 537).
- EOD never clears a kill it did not set. If it did set one, it resumes it at step 14 (EOD_SQUAREOFF_COMPLETE).
- Entries are also closed by the 15:00 window and the 15:15 placement cut-off independently (B-009).

B10-C3. What Pass 1 cancels (FACT, SOURCE-VERIFIED)
- Entries: get_pending_intraday_orders (state_store.py 1015-1039) selects trades with status = 'PENDING_FILL' whose ENTRY order has product MIS or CO.
  - Each one: cancel_order; on success the trade and order are set CANCELLED and the reservation released (884-928).
  - On failure: CRITICAL log, failed += 1, continue (886-892, 930-943).
- Exit legs: get_pending_exit_orders_for_open_positions (1135-1168) selects non-terminal SL and TGT orders of OPEN or PARTIAL trades whose entry product is MIS or CO.
  - Each one is cancelled with its variety; on success the order row is set CANCELLED (981-1007).
  - Per-row failures are logged CRITICAL and counted, without stopping. A failed fetch skips the whole step (960-968).
- No failure aborts Pass 2.
- KNOWN DEFECT (source path): the entry selection keys on 'PENDING_FILL'.
  - OrderManager inserts a trade as PENDING_FILL (orders/order_manager.py 13, 198, 236), but OrderPlacer sets it to "PENDING" before the broker call (order_placer.py 1061-1071).
  - No runtime code sets PENDING_FILL afterwards. Search across the 330 files: no UPDATE to 'PENDING_FILL'; the trade-status updates are listed in the companion file.
  - So a trade with an entry order resting at the broker reads PENDING, and Pass 1 cannot select it.
  - tests/unit/test_eod_squareoff.py 1080-1081 seeds PENDING_FILL directly ("create_trade sets status=PENDING_FILL already"), so the test does not exercise the placer's transition.
  - INTERPRETATION of the effect: small at 15:17. The order monitor's 60 s fill timeout and the 15:15 entry cancellation would normally have cancelled any entry already, but both depend on the monitor running (B-009 D3).

B10-C4. Why EOD waits between the passes (FACT, SOURCE-VERIFIED)
- The 2 s sleep (417-424) is FIX-063. The rationale is in its comment: a "phantom fill" arriving as the cancel is sent should reach the order monitor (2 s poll), the state machine and the DB, and then appear in the open-position query.
- INTERPRETATION: this is intended, not guaranteed. One 2 s monitor cycle may or may not have run in that window, and the trade-status update depends on the event chain.
- The broker-position filter in Pass 2 (1065-1120) is the stronger guard: it re-reads broker positions before exiting.

B10-C5. How positions are selected for exit (FACT, SOURCE-VERIFIED)
- Local rows come from get_open_intraday_positions (state_store.py 1207-1250): status OPEN or PARTIAL, qty_filled > 0, ENTRY product MIS or CO, grouped by trade and sorted by symbol.
- Broker filter: get_positions once, keeping symbols with non-zero quantity and product in EMERGENCY_FLATTEN_PRODUCTS ({MIS, CO}; 1071-1087).
  - Local rows whose symbol is absent at the broker are skipped, with a warning (1104-1120).
  - If the broker read fails, the filter is skipped and the DB quantity used (1088-1094).
- Quantity: the broker's absolute quantity for that symbol replaces the row's (1257-1260). Zero means skip without counting (1261-1272).
- DELIVERY/CNC is excluded by both the local and the broker filter.
- CO: a branch exists (order_protocol CO_PLUS_TGT with entry variety "co"; 1166, 1172-1247). It cancels the CO bracket instead of placing a reverse order.
  - On the traced placement path no order is CO_PLUS_TGT (B-009 D2), so this branch is latent.
  - FACT (RECORD-DERIVED, a comment at mis_autosquareoff.py 86-87 citing a query): "SELECT DISTINCT product FROM orders = {MIS, CNC}". No date is given.
- Residual sweep: a second, fresh get_positions (1446-1454) finds non-zero MIS/CO broker positions not already handled. Only those whose symbol has a local trade today are flattened; others are logged as human and skipped (1456-1513).
- INTERPRETATION: quantity is keyed by symbol, not by trade. Two local OPEN trades on one symbol would each be sent the full broker quantity. The skip on a later zero read applies only after the first exit fills, which is not awaited. Not established that this ever occurred.

B10-C6. Order type and price (FACT, SOURCE-VERIFIED)
- With exit_protocol LIMIT_THEN_MARKET (config 363):
  - one batched get_quote (1135-1150);
  - a LIMIT at LTP x (1 - 0.01) for a SELL, or x (1 + 0.01) for a BUY (1275-1287);
  - if there is no LTP, MARKET (1288-1295);
  - place_order with intent INTRADAY and tag EOD_SQUAREOFF (1300-1308);
  - 0.5 s between orders (1378-1380).
- After all symbols: one 120 s sleep (1386-1393). Then _promote_limits_to_market re-reads positions, cancels each LIMIT still open and places MARKET for the remaining quantity (1592-1722). If that re-read fails, LIMITs are left in place (1617-1627).
- Residual sweep: a marketable LIMIT at LTP +/- the emergency buffer, or MARKET when there is no LTP (1516-1590).
- KNOWN DEFECT (source plus records): every MARKET placed by EOD omits market_protection. That covers the no-LTP fallback (1294), the promotion (1663-1671) and the residual fallback (1547-1548).
  - The adapter sends no protection band when none is given (broker/zerodha_adapter.py 2116-2119).
  - FACT (RECORD-DERIVED):
    - docs/audit/MIS_SQUAREOFF_REJECTION_IDEA_10-Sep-2026.md line 21 records the broker refusing a MARKET order: "Market orders without market protection are not allowed via API" (10-Sep-2026, production);
    - order_placer.py 137-138 quotes the same rejection from 15-Jun;
    - docs/incident/2026-09-03_naked_position_ANANTRAJ.md lines 128-131 list these EOD MARKET call sites (at deployed 2d08436).
  - INTERPRETATION: such an EOD MARKET order would be refused, counted as failed (promotion) or caught (residual), and the position left to the broker's auto square-off.
  - FACT (RECORD-DERIVED, same incident, lines 312-315): the 27 EOD-leg orders ever placed up to 03-Sep were all LIMIT. No EOD MARKET is recorded as executed.

B10-C7. Exit legs before flattening (FACT, SOURCE-VERIFIED)
- Pass 1b cancels SL/TGT before Pass 2 (402-410). If a leg's cancel fails, Pass 2 still runs (comment at 403-406; code continues).
- INTERPRETATION: a surviving SL or TGT could fill after the EOD exit and open a reverse position. The comment names that risk (402-404).
- The later stale-order sweep (order_reconciler.py 472-537) only marks local orders CANCELLED when their parent trade is already terminal. It makes no broker call and so cannot cancel a live leg.

B10-C8. Does EOD wait for fills or a flat book? (FACT, SOURCE-VERIFIED)
- No. The module says fill confirmation is out of scope (EOD7, 25; 35). EOD hands each exit to OrderMonitor.track with leg "EOD" (1313-1323, 1560-1571, 1672-1682) and records an orders row.
- positions_succeeded counts exit orders placed (1352), CO cancels accepted (1241), promotions placed (1701) and residual orders placed (1503-1504). It does not count fills.
- A later fill reaches the placer only through the order monitor's events. The reconciler's 15 s checks pick up the rest (B-009 section 8).
- EodSquareoffComplete and the COMPLETE row do not prove a flat book.

B10-C9. EodFireResult (FACT, SOURCE-VERIFIED)
- Fields (eod_squareoff.py 77-89): fired_date, fired_at, positions_attempted/succeeded/failed, cancels_attempted/succeeded/failed, duration_sec, recovery_fire.
- Built at 546-557 and returned.
- Consumers:

- The same counts go to the log line (452-457), the eod_squareoff_log row (465-497) and the event (514-525). recovery_fire is only in the result object; it is not persisted.

B10-D2. PASS 1 (FACT, SOURCE-VERIFIED)

B10-D4. Post-pass verification and the 15:09 deadline (FACT, SOURCE-VERIFIED)

B10-D5. Restoring protection (FACT, SOURCE-VERIFIED)
- _restore_protection is called on the cancel-failed path (850) and the exit-raised path (904). It never raises (917-943).
- Steps (945-1131):
  1. Recover the original SL row from the local orders table; if absent, "RESTORE FAILED: original SL parameters not found".
  2. Side-scoped idempotency against the broker's open orders. A read failure gives PROTECTION_UNKNOWN and the restore proceeds.
  3. Re-place the SL with the original parameters.
  4. Verify by polling order history up to 5 s (1133-1175):
     - TRIGGER PENDING or OPEN: RESTORE_CONFIRMED;
     - REJECTED or CANCELLED: RESTORE_FAILED;
     - COMPLETE: RESTORE_FILLED;
     - timeout: PROTECTION_UNKNOWN.
- The TGT is deliberately not restored (929-930).
- Cases where restoration cannot be established: no local SL row; an empty broker id (1075-1085); PROTECTION_UNKNOWN; or the restore itself raising.
- FACT (RECORD-DERIVED, 10-Sep record line 22): "RESTORE FAILED: original SL parameters not found" occurred for a position with no local trade (IDEA).

SECTION E — FAILURE, PARTIAL SUCCESS, AND RECOVERY

B10-E1. Partial failure (FACT, SOURCE-VERIFIED)
- Every per-item cancel or exit failure is logged CRITICAL, counted and skipped, with no abort (886-892, 930-943, 985-1023, 1360-1376, 1707-1716).
- Exit failures also set the trade's exit_reason to EOD_EXIT_FAILED (1724-1734).
- Unguarded store reads can abort the run (B4).
- Alerts: there is no dedicated per-failure Telegram message in EOD. Failures appear in the CRITICAL log, the counts, the event and the log row; the daily summary does not report them.

B10-E2. Broker queries failing (FACT, SOURCE-VERIFIED)
- EOD:
  - positions read fails: fall back to the DB view and quantity, a fail-toward-squaring choice (1088-1094);
  - quote fails: MARKET for all (1144-1150);
  - promotion re-read fails: LIMITs stay (1617-1627);
  - residual read fails: sweep skipped (1446-1454);
  - trades read fails: all residuals treated as system-owned (1473-1480).
- MIS unit: every read failure gives BROKER_STATE_UNAVAILABLE or RECONCILIATION_UNKNOWN and no exit; "a failure is never flat" (443-456, 1223-1233).
- Local trade rows can differ from broker truth. EOD's filter and the MIS unit's broker-only view exist because of that (comments 1053-1061, 745-752).

B10-E3. Write-ahead persistence (FACT, SOURCE-VERIFIED)
- IN_PROGRESS: INSERT OR REPLACE on the unique fired_date (state_store.py 1348-1368), at step 3. A failure is logged and the run proceeds (368-378).
- COMPLETE: UPDATE ... WHERE fired_date (1370-1406). The fallback insert (insert_eod_squareoff_log, INSERT OR REPLACE, 1310-1346) runs only if the UPDATE raises (476-492). If both fail: EOD_LOG_PERSIST_FAILED, CRITICAL (493-497).
- KNOWN DEFECT (source path): the UPDATE does not check how many rows it changed (1386-1406).
  - If the write-ahead insert had failed, the UPDATE changes no row and raises nothing, so the fallback is not reached and no row exists for the date.
  - The comment at 478-480 ("Guarantees we always have a COMPLETE row") does not hold on that path.
  - INTERPRETATION: a restart later the same day before 15:30 would then find no row and recovery-fire a second EOD (E4).

B10-E4. Restart recovery (FACT, SOURCE-VERIFIED; _check_restart_recovery 1736-1887, via post_wire_init at main.py 3866)
1. Row COMPLETE (or no status column, read as COMPLETE): mark fired; warn if it recorded failures; no retry (1763-1775).
2. Row IN_PROGRESS: CRITICAL; mark fired; _fire(recovery_fire=True) (1777-1788).
   - On an exception: CRITICAL plus a notifier alert ("EOD Recovery Failed"), with no flag reset and no retry (1789-1816).
   - This path checks neither the time nor holidays.
3. No row, before EOD time, or a holiday: return (1819-1823).
4. No row, after market_close 15:30: CRITICAL. If open intraday positions remain (or the count is unknown), write a system event EOD_SKIPPED_LATE and send an alert; no fire (1825-1877).
5. No row, between the EOD time and 15:30: warning; mark fired; _fire(recovery_fire=True) (1879-1887). An exception here is not caught inside the method.
- With recovery_fire set, rows are trimmed to what the broker still shows. The filter now applies to every fire (1096-1103).
- A helper existing is not proof that the host restarted or that recovery succeeded: UNKNOWN for any date. Restart in general: DEFER TO B-012.

B10-E5. Idempotency and retries (FACT, SOURCE-VERIFIED)
- check_and_fire:
  - resets its flag only on an exception (229-235), not on a partial failure;
  - a partial scheduled run is final for the day in that process.
- fire_now:
  - resets on an exception and on a partial failure (273-288), so the 15:17 run repeats the sequence;
  - a full success blocks the 15:17 run.
- Repeated effects of a rerun:
  - INSERT OR REPLACE of the date row (one row per date; the earlier run's counts are overwritten);
  - a second soft_kill/resume cycle;
  - a second checkpoint and event;
  - a second RESET_PNL ledger row with pnl_delta = -current net. Documented at 252-256 and asserted by tests/unit/test_fire_now_retry_resets_daily_pnl_twice_nonzero, test_eod_squareoff.py 787.
- Double exits are guarded only by the broker re-read at the second run (1104-1120). INTERPRETATION: exits from the first run that have not yet filled are not visible to that re-read.

B10-E6. Order monitor, reconciler, supervisor, 15:15 (source facts, with host unknowns)
- FACT (SOURCE-VERIFIED):
  - EOD does not need the order monitor to run its sequence; track() only registers.
  - If the monitor has stopped (B-009 D3):
    - EOD exits are not polled into fill events;
    - the 15:15 tracked-entry cancellation does not run, so EOD's own SOFT_KILL step sets the kill.
  - The reconciler's 15 s cycle is independent of EOD.
  - Liveness: eod_scheduler, order_monitor and order_reconciler are on /health (main.py 4060-4071); the MIS unit is not (D1).
- UNKNOWN / NOT ESTABLISHED: any external supervisor's behaviour, and whether any of these threads stopped on any date.

B10-E7. Daily-loss closure (FACT, SOURCE-VERIFIED; main.py 756-817)
1. CRITICAL log, then a "DAILY LOSS LIMIT HIT" Telegram alert (775-792).
2. fire_now. EOD's _fire sets SOFT_KILL if none is active and resumes it at its own step 14.
3. The callback then sets SOFT_KILL (811-814) whether fire_now succeeded, raised (802-805) or EOD was absent (806-809).
- INTERPRETATION: between EOD's resume and the callback's soft_kill there is a short interval with no kill active.
- Positions that remain after a partial run are retried by the 15:17 run (E5).
- Trigger: FundManager's on_daily_loss_breach, fired post-trade (fund_manager.py 21, 306, 342). Detailed semantics: DEFER TO F and I topics.

B10-H1. An ordinary scheduled day (source path)
1. 15:03 and 15:06: MIS passes on broker MIS positions (D2-D4). Their exits are not written locally (async: fills reach local trades only via reconciler CHECK1).
2. 15:15: placement cut-off; tracked-entry cancellation and SOFT_KILL, if the order monitor runs.
3. 15:17:00 to 15:17:05: the eod_squareoff_poll sees the time due, and check_and_fire claims the date.
4. _fire:
   a. gate clear (inert);
   b. IN_PROGRESS row;
   c. kill already active, so no change;
   d. Pass 1 cancels (entries: none selectable, D-2; SL/TGT legs);
   e. 2 s;
   f. Pass 2: local OPEN rows filtered by broker positions; LIMIT at LTP +/- 1%; tracked by the order monitor (async);
   g. 120 s; promotion of unfilled LIMITs to MARKET (D-3);
   h. residual sweep;
   i. stale sweep;
   j. COMPLETE row;
   k. checkpoint;
   l. event;
   m. RESET_PNL;
   n. no resume;
   o. summary alert (before fills).
5. After that: fills via order-monitor events; the reconciler's 15 s cycle (async).
6. 15:45 onward: cron jobs (declared).
7. 17:35: self-exit (B-011).

B10-H2. Daily-loss path
- Any time intraday (holiday and time checks bypassed): the callback alerts, then fire_now runs the same _fire (with SOFT_KILL set and resumed by EOD), then the callback sets SOFT_KILL.
- If fully successful, 15:17 does not run that day. On a partial failure or an exception, 15:17 runs the full sequence again (E5), with a second RESET_PNL.

B10-H3. Failure and restart traces (source path; host behaviour UNKNOWN)
| Case | Source path |
|---|---|
| Crash after IN_PROGRESS | The row stays IN_PROGRESS; at the next start the same day, recovery fires at any time of day without a holiday check (E4.2) |
| Cancellation failure | Counted, continue (E1) |
| Exit failure | Counted, EOD_EXIT_FAILED, continue (E1) |
| Exception before COMPLETE | Scheduled: flag reset, retry each 5 s; SOFT_KILL set by EOD stays set; the row stays IN_PROGRESS until a run completes. fire_now: flag reset, the exception reaches the daily-loss callback, SOFT_KILL set |
| COMPLETE persistence failure | Fallback insert; if both fail, CRITICAL. If the write-ahead had failed, the UPDATE matches nothing and no row is written (D-4) |
| Partial failure without exception | Scheduled: final for the day. fire_now: 15:17 reruns |
| Recovery after restart | E4 cases 2 and 5 |
