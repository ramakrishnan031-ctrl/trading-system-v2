1. SUMMARY
==============================================================================
- One HTTP server carries the webhook: waitress 3.0.2 serving WebhookReceiver's Flask app in the trading
  process (daemon thread "webhook-server"; bind host and port 5000 from the configuration; 8 threads; connection
  limit 100; plain HTTP). It has two routes: POST /webhook/<scanner_name> and the WEBHOOK /health (GET). A
  separate health server on port 8080 does not carry the webhook (Q7.8).
- Sender side: nothing in the repository holds the webhook URL that Chartink was given. The map holds the key
  that must equal the path segment, the system configuration holds the port, and the token sits in the
  environment (C-003). Three records outside the code give the URL form: a 15-Jul specification handed to Rama,
  a unit-test fixture, and Rama's account of 21-Oct (C-001 section 9.2): plain HTTP to the VM's address on port
  5000, /webhook/<key>, and a ?token= parameter.
- Contract: POST; the body is read as raw bytes up to 1 MiB, whatever the content type, and parsed as a JSON
  object. In order: 503 while shutting down, 429 above the per-address limit, 401 without valid authentication,
  404 for an unknown key, the EOD route for an eod key, 403 under the kill switch, 503 under backpressure, 403
  outside the entry window, 400 for parse, field or alert-name failures; then 200, or 503 if any symbol was
  QUEUE_FULL or STORE_ERROR, with per-symbol results. Requests the framework answers itself (a wrong path or
  method, or a body over the limit) never reach the audit write.
- Hand-off: per symbol, a signals row (QUEUED) and a tuple on a bounded in-memory queue read by SignalProcessor
  (C-005 to C-009); an eod key goes to the watchlist capture worker (C-011).
- Arrival records (FACT (RECORD-DERIVED)): webhook_audit starts on 12-Jun-2026; 104,911 POSTs to 23-Jul and
  127,272 rows to 31-Jul; to 23-Jul only 200, 403 and 18 x 503 were answered, with no 400, 401, 404, 429 or 500;
  one Chartink address sent 99.99% of requests from 12-Jun to 03-Jul; Chartink posted each scanner about once a
  minute (09-Jul). Times when the service was down left no row (the 19-Jun gap; PB-01's 17:00 alerts of 13 to
  24-Jul). From 05-Jul the VM's firewall admitted port 5000 from that one address only (recorded on 05 and 06-Jul;
  its later state is not established).
- Not established: Chartink's configuration, retries and timeouts; whether any alert was attempted when the port
  was closed, beyond the PB-01 record; the VM's later network state; installed library versions; anything after
  the last record (31-Jul, with one 03-Aug note).
