4. THE AUTHENTICATION DECISION (_authenticate)
==============================================================================

4.1 Location and callers. FACT (SOURCE-VERIFIED). WebhookReceiver._authenticate(hmac_payload: bytes) returns
    (True, "") or (False, reason). Since C6 (25-Jul) it is the only place either comparison is made: /webhook calls
    it with the raw body, /health with b"". No other caller in S-ALL (search T01: the receiver, its tests and
    records, and, because the search matches part of a word, a differently named dashboard function
    (is_authenticated), its test file and an integration-test fixture name; none calls the receiver's method, and
    the dashboard's authentication is not C-003's subject).
    Evidence: signals/webhook_receiver.py lines 298 to 325; signals/webhook_receiver.py line 387;
    signals/webhook_receiver.py line 547; ops_dashboard/backend/auth.py line 256.

4.2 Branch order and exact predicates. FACT (SOURCE-VERIFIED) unless marked.
    B0  not self._secret (None or "")              -> (True, ""). No header or query is read. Test-only path (2.6).
    -   reads sig_header = request.headers.get("X-Webhook-Signature", "") and
        token_param = request.args.get("token", "").
    B1  sig_header.startswith("sha256=")           -> expected = HMAC-SHA256(key = self._secret.encode() [UTF-8],
        message = hmac_payload).hexdigest() (lower-case hex); compare_digest(sig_header[7:], expected):
        unequal -> (False, "HMAC signature mismatch"); equal -> (True, ""). Terminal: the token is not consulted, so
        a valid ?token= cannot rescue a wrong signature. The code comment says the same; one test isolates it, with
        require_hmac False (the C6 test below); two tests run with require_hmac True, where B2 would refuse the token
        anyway, so they do not isolate it (the G.1 test and its /health mirror below).
    B2  self._require_hmac (no "sha256=" header)   -> (False, "HMAC signature required (require_hmac=True); token
        param is not accepted"). The token is not consulted.
    B3  token_param non-empty                      -> compare_digest(token_param, self._secret): unequal ->
        (False, "Invalid token"); equal -> (True, "").
    B4  otherwise                                   -> (False, "Missing auth: provide X-Webhook-Signature header or
        ?token= param").
    Evidence: signals/webhook_receiver.py lines 326 to 354; tests/unit/test_c6_auth_collapse.py lines 184 to 194;
    tests/unit/test_webhook_receiver.py lines 1269 to 1287;
    tests/unit/test_fix134_backpressure.py lines 315 to 322.
    Predicate details:
    - The prefix test is case-sensitive: "SHA256=..." is not a signature and falls to B2, B3 or B4 (CURRENT
      EXTERNAL FACT, probe: Python's str.startswith). The hex must be lower case to match hexdigest().
    - A header present without the prefix is ignored: with require_hmac False it is the token (B3) or B4 that
      decides.
    - An empty ?token= gives "" and falls to B4; when the parameter repeats, request.args.get returns the first
      value (CURRENT EXTERNAL FACT, probe of Werkzeug 3.1.9).
    - What is signed: on /webhook the exact bytes request.get_data() returned (the raw body as received, read
      before any parsing; not parsed or re-serialised JSON); on /health the empty byte string. Neither the path,
      the method, the query, a time stamp nor a nonce is covered.
      Evidence: signals/webhook_receiver.py line 480; signals/webhook_receiver.py line 511;
      signals/webhook_receiver.py line 387.
    - Both comparisons are hmac.compare_digest on two str values. CURRENT EXTERNAL FACT (probe, Python 3.13.16):
      compare_digest raises TypeError ("comparing strings with non-ASCII characters is not supported") when either
      string has a non-ASCII character; through Flask's test client, a query value such as %C3%A9 arrives as a
      non-ASCII str, and so does a header byte above 0x7F (Werkzeug decodes headers as latin-1). On the serving path
      waitress parses the request first; that path was not probed. _authenticate does not catch the error.
      What each route then answers: 5.3 row 10 and 6.2 row 5 (K-03).

4.3 Decision table (S = secret configured; R = require_hmac as resolved; H = the X-Webhook-Signature header;
    T = the token query parameter). "Pass" means _authenticate returned True; what follows depends on the route.

    #  | S   | R     | H                              | T                      | Branch | Result                          | /webhook             | /health
    1  | no  | False | any                            | any                    | B0     | pass (test-only path)           | continues (5.3)      | 200 with state
    2  | yes | any   | "sha256=" + correct hex        | any                    | B1     | pass                            | continues            | 200 with state
    3  | yes | any   | "sha256=" + anything else      | any (valid or not)     | B1     | "HMAC signature mismatch"       | 401, that message    | 401 uniform
    4  | yes | any   | "sha256=" + a non-ASCII char   | any                    | B1     | TypeError raised                | 500 (audited)        | 500 (handler)
    5  | yes | True  | absent or other form           | any                    | B2     | "HMAC signature required ..."   | 401, that message    | 401 uniform
    6  | yes | False | absent or other form           | non-empty, equal       | B3     | pass                            | continues            | 200 with state
    7  | yes | False | absent or other form           | non-empty, unequal     | B3     | "Invalid token"                 | 401, that message    | 401 uniform
    8  | yes | False | absent or other form           | non-ASCII              | B3     | TypeError raised                | 500 (audited)        | 500 (handler)
    9  | yes | False | absent or other form           | absent or empty        | B4     | "Missing auth: ..."             | 401, that message    | 401 uniform

    Rows 3 and 7 are for ASCII values; a non-ASCII value is rows 4 and 8. Row 1 has R False: BL-18 refuses
    require_hmac True without a secret at construction (3.4). Rows 4 and 8 are INTERPRETATION from the source and
    the probe (the legacy code was not run). The pinned configuration gives R = False (3.3), so rows 6 to 9 were
    the token rows at the repository level.
    Evidence: signals/webhook_receiver.py lines 326 to 354; signals/webhook_receiver.py lines 177 to 182;
    signals/webhook_receiver.py line 480; signals/webhook_receiver.py line 387;
    tests/unit/test_c6_auth_collapse.py lines 262 to 280.

4.4 Replay and binding. INTERPRETATION / AUDIT LEAD (L-01), from 4.2:
    - /health: the valid signature is HMAC-SHA256(secret, b""), a constant; whoever saw one header could reuse it
      indefinitely (the docstring says so: "a CONSTANT for a given secret and indefinitely replayable").
    - /webhook: a signature binds the body, not the path, so a captured signed body would pass auth on any
      /webhook/<key> path. On the intraday path, scan_name in the body, when present, must still match the path
      after auth (C-002 section 8.3), and repeats are limited after auth by the expiry check, the dedup cache and the
      fingerprint, not by the auth decision. The EOD route checks none of these: it parses the body, checks three
      fields and triggered_at and hands each symbol to the capture worker, so a captured body with those fields is
      accepted again on any "eod" path (the capture worker's own handling was not read).
    - Empty body: the constant /health signature also authenticates a POST to /webhook whose body is empty (4.3). Such
      a request gets whichever answer after authentication applies (the unknown-scanner 404, which tells whether a
      name is a configured scanner; the EOD route; the kill-switch 403; the backpressure 503 with its queue-depth
      header; the window 403), and otherwise ends with a 400 for malformed JSON (two WARNINGs on the intraday path,
      one on an "eod" path, each holding the empty body); no signal can be accepted this way. The docstring's
      "body-bound" has this exception.
    - Query token: a static bearer value; anyone holding the URL could authenticate any body to any path and read
