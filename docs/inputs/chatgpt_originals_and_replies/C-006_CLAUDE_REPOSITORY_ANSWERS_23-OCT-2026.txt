SUMMARY
==============================================================================
- One standard-library queue.Queue(maxsize=300), built in main and shared by the receiver (producer) and the processor
  (consumer). The receiver refuses a whole request with 503 when the queue holds 240 or more (80%), and marks a symbol
  QUEUE_FULL when its put finds the queue full; the request then answers 503, which the code's comment calls the sender's cue to
  retry (R 59-63). FACT (SOURCE-VERIFIED); whether a sender retried is not established.
- The receiver writes the signal row as QUEUED and commits it before the put; a full queue changes the row to QUEUE_FULL. A
  later request with the same fingerprint re-queues that row under its old signal_id. FACT.
- One dispatcher thread takes items and submits each to a pool of 5 workers at once; the queue's depth counts only items the
  dispatcher has not yet taken. FACT; consequence INTERPRETATION (C6-L4).
- Three re-queue paths exist in code; one of them (the FIX-007 rate-limit pre-check) is not wired at the pin. FACT.
- A clean stop drains the queue into the pool and rejects a drained signal as REJECTED_SHUTDOWN only when it reaches placement;
  items put after the final drain are not processed (INTERPRETATION, C6-L3). A crash loses the queue; nothing found re-queues
  QUEUED rows at the next start. FACT (bounded by Q10).
- Eight cross-topic bookmarks (section 7), including BK-04 (C-005 BM-02/C5-L4), re-verified and extended.

- [Q1-b] FACT (SOURCE-VERIFIED): the setting is declared by SignalQueueConfig (CL 192-197; extra keys forbidden): capacity int,

  validator (the next class starts at CL 200). The system model holds it as signal_queue (CL 1991).
- [Q1-c] FACT (CONFIG): CFG 124-128: signal_queue capacity 300, backpressure_pct 0.80, expiry_sec 600, warning_pct 0.60.

Q2. Where is the backpressure threshold set, and is it applied before parsing, per request or per symbol?
- [Q2-a] FACT (SOURCE-VERIFIED): threshold = int(capacity x backpressure_pct) (R 571-573; CFG 125-126). The gate runs once per
  request inside _process_request (R 570-578): after the shutting-down check and the per-IP limit (R 483-504), authentication
  (R 547-549), the unknown-scanner check (R 552-554), the EOD branch (R 562-564) and the kill switch (R 566-568); before the
  entry-window check (R 580-583) and before the per-symbol loop (R 696). At qsize() >= 240 it answers 503
  {"error": "Signal queue at capacity; retry later"} with X-Queue-Depth (R 575-578). It is per request, not per symbol. The
  body parsing between R 584 and R 676 was not read in C-006 (B-008, HISTORICAL, places the window check before it).
- [Q2-b] FACT (SOURCE-VERIFIED): per symbol, only put_nowait raising queue.Full detects a full queue (R 1048-1050; R 994-996 on
  the re-queue path), giving QUEUE_FULL. The request answers 503 when any symbol is QUEUE_FULL or STORE_ERROR (R 59-66,
  730-734); the other symbols' results in the same answer stand.
- [Q2-c] FACT (EXTERNAL): qsize() is approximate. INTERPRETATION: the gate reads the depth once per request while up to 8 request
  threads (M 3994) put concurrently, and one admitted request can carry many symbols, so the queue can pass 240 and reach 300;
  symbols after that get QUEUE_FULL.
- [Q2-d] FACT (SOURCE-VERIFIED): warning_pct only adds X-Queue-Warning: high to the batch answer when the depth after the loop is
  180 or more (R 574, 741-744); it refuses nothing.

Q6. What happens to queued items at stop, at a kill switch and at a crash, and what does the next start do with rows left QUEUED?
- [Q6-a] FACT (SOURCE-VERIFIED): stop order: main stops the receiver, then the processor (M 1681-1692). The receiver's stop() sets
  its shutting-down flag and returns (R 1166-1176); new requests then get 503 "Service shutting down; retry later" and an audit
  row (R 483-490). It does not wait for requests already past that check (R 1166-1176; the comment at R 210-213 says they "drain
  naturally").
- [Q6-b] FACT: the processor's stop() sets its stop flag (P 333); the dispatcher leaves its loop and submits every item still in
  the queue to the pool (P 392-399); main's thread joins the dispatcher for up to 10 s (P 336) and then waits for all submitted
  work with no time limit (P 338-340). FACT (TEXT DRIFT): the docstring says "up to 5s per SP4" (P 327-329); B-006 records the
  same.
- [Q6-c] FACT: a drained item runs the normal pipeline: PROCESSING (P 897), then the stages; if it reaches placement, the stop
  flag rejects it as REJECTED_SHUTDOWN and releases its reservation (P 1398-1405, 1193-1201). An earlier stage rejects with its
  own status (for example P 905-912). INTERPRETATION: so not every drained signal ends as REJECTED_SHUTDOWN.
- [Q6-d] INTERPRETATION (code path, not observed): an item put after the dispatcher's final drain, by a request that passed R 485
  before the flag was set or by a worker's re-queue (P 1520; P 426 if wired), is taken by no one; at exit it is lost and its row
  keeps QUEUED or PROCESSING. C6-L3, bookmark C-006/BM-03.
- [Q6-e] FACT (SOURCE-VERIFIED): kill switch: a new request gets 403 "Kill switch active; signals rejected" before the queue gate
  (R 566-568). Items already queued stay queued and are rejected one by one when processed: REJECTED_KILL_SWITCH (P 905-907), or
  REJECTED_KILL_SWITCH_LATE before placement (P 1396). No kill-switch module names the queue (Q02, Q24).
- [Q6-f] FACT: crash: the queue lives only in process memory (M 3402), so its items are lost; their rows keep QUEUED or
  PROCESSING, and QUEUE_FULL rows stay QUEUE_FULL. HISTORICAL: A-011 Q32 and B-006 say the same.
- [Q6-g] FACT (bounded by Q10): next start: the queue is built empty (M 3402), and nothing found re-queues QUEUED rows. In runtime
  files QUEUED appears in R only in the INSERT (R 977), the flip (R 1005) and comments or log text (R 812, 985, 1011), in reports

  changes rows still PROCESSING from earlier days to EXPIRED and leaves QUEUED and QUEUE_FULL rows unchanged (EC 105-127). When EC
  runs is B-010's; restart is B-012's.

5. NEW LEADS AND OPEN QUESTIONS (not resolved; INTERPRETATION unless marked)
==============================================================================
- C6-L1. INTERPRETATION. Re-queue flip order: the receiver puts the item (R 995) before it sets the row to QUEUED (R 1003-1007),
  and that UPDATE has no condition on the current status. A worker that writes PROCESSING (P 897), or a fast rejection, before the
  flip would be overwritten by QUEUED; if the worker's last write came first, the row would end QUEUED.
- C6-L2. INTERPRETATION. A failed QUEUE_FULL mark (R 1052-1059) leaves the row QUEUED with no queue item; the request still
  answers QUEUE_FULL (503). A retry in the same fingerprint bucket then meets that row with status QUEUED and is answered
  DUPLICATE (R 981-1015), so the signal would never be processed and its row would stay QUEUED.
- C6-L3. INTERPRETATION. Items put after the dispatcher's final drain, by a late receiver request (R 485, 1166-1176) or a worker's
  re-queue during stop (P 1520), are not processed (P 392-399); at exit they are lost and their rows stay non-terminal (Q6-d).
- C6-L4. INTERPRETATION. The queue's depth excludes work waiting in the pool (P 383-390; Q4-d), so the 503 gate and QUEUE_FULL
  react only when the dispatcher falls behind; whether they ever did at runtime is not established.
- C6-L5. INTERPRETATION. A re-queued QUEUE_FULL row keeps the first attempt's price and time while the item carries the retry's
  (R 993, 1005; Q3-e).
- C6-L6. INTERPRETATION. The pre-check path's full-queue branch reads signal_tuple[1] (P 429); for a dict item that indexes a dict
  by position and would raise before the status write and the release (P 434-460). The path is not wired at the pin (Q5-f).
- C6-L7. FACT (TEXT DRIFT), recorded only: CL 196 (expiry default 60); P 327-329 ("up to 5s"); P 1489 ("45s total, 15s each");
  TSMV 64-109 (DROPPED_* statuses that runtime code does not write, Q28).
