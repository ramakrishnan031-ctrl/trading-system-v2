# 3. LEGACY CAPITAL MODEL — DOCUMENTED AS-IS

## 3.1 Capital domains

The legacy system maintained separate capital buckets:
- Intraday
- Positional / Delivery

Cross-bucket borrowing was documented as forbidden.

Production configuration contained:
- `capital.intraday_bucket_pct`
- `capital.positional_bucket_pct`
- `conditional_allocation_enabled`
- `capital.slm_margin_buffer_pct`
- `capital.sl_limit_offset_pct`
- `capital.gtt_sl_limit_offset_pct`
- `capital.emergency_exit_buffer_pct`
- `leverage_map`.

The preserved configuration contained historical comments describing a
real-cash / planning-basis distinction and separate Delivery values. Because
these values changed historically and conflict with some earlier recollections,
the manual records the configuration as evidence rather than normalising it
into one timeless number.

## 3.2 Legacy PositionSizer

`capital/position_sizer.py` converts a candidate signal into an integer quantity.

Documented inputs include:
- symbol
- side
- entry price
- stop-loss
- intent/product
- score/tier
- FundManager capital snapshot
- optional lot size
- optional broker live-margin percentage.

The preserved working-tree documentation records this legacy formula family:

`risk_per_trade_rs = total_capital × effective_risk_pct`

`sl_distance = abs(entry_price - sl_price)`

`qty_by_risk = floor(risk_per_trade_rs / sl_distance)`

`effective_entry_price = entry_price × (1 + entry_offset_pct)`

`margin_per_share = effective_entry_price / leverage`

`qty_by_capital = floor(available_bucket / margin_per_share)`

`qty_by_concentration = floor((total_capital × effective_concentration_pct) / entry_price)`

`raw_qty = min(qty_by_risk, qty_by_capital, qty_by_concentration)`

`tiered_qty = floor(raw_qty × tier_multiplier)`

`final_qty = floor-to-lot-size(tiered_qty)`

The sizer can use a broker live-margin percentage when available and has a
fallback/static-leverage path in the preserved legacy evidence.

IMPORTANT: this describes the preserved legacy implementation/formula family.
It is not a V2 formula freeze.

## 3.3 Legacy FundManager

`capital/fund_manager.py` is the documented capital-ledger authority.

Core invariant:

`available + reserved + used == total`

Legacy lifecycle:

`AVAILABLE → RESERVED → USED → AVAILABLE + realised P&L`

Rejected/cancelled pre-fill path:

`RESERVED → AVAILABLE`

Reservation occurs before broker order placement.

The documented reservation sequence is:

1. determine bucket;
2. calculate required margin;
3. add configured SL-M buffer where applicable;
4. check availability;
5. write `RESERVE` ledger row;
6. apply reservation;
7. verify invariant;
8. return reservation ID.

Every capital mutation is written to `fm_ledger` using write-ahead behaviour.

# 6. FUTURE CAPITAL FORMULAS

### Base maximum cash allocation

`base_max_cash_per_trade = locked_segment_capital / configured_trade_divisor`

### Actual cash allocation

`actual_cash_allocation = MIN(base_max_cash_per_trade, current_available_segment_capital)`

This means:
- if available capital is greater than the normal allocation, spending remains
  capped at the normal allocation;
- if available capital is lower, the lower amount is used.

### Broker permitted notional

`permitted_notional = actual_cash_allocation / broker_required_margin_pct`

The spreadsheet wording “Capital available after Margin” is therefore documented
as **permitted/derived notional**, not remaining cash.

### Quantity

`quantity = FLOOR(permitted_notional / intended_entry_price)`

Then apply actual instrument/lot constraints.

# 7. DAILY FILLED-TRADE LIMIT

Confirmed intended rule:

- maximum daily trade count = broker-filled trades;
- pending/queued orders do not count as filled;
- cancelled orders do not count;
- rejected orders do not count;
- the system continues processing later candidates after cancellation/rejection;
- processing stops for new trades once the configured filled-trade maximum is reached.

This is separate from capital/margin calculation.

A pending order can still be relevant to broker margin/execution safety even though
it is not a completed trade for the daily count.

# 8. DAILY MARGIN / CAPITAL LOCK

Confirmed intended sequence:

```text
SYSTEM BOOT
 → ZERODHA TOKEN / INSTRUMENT UPDATES
 → MARGIN DB REFRESH (~08:30)
 → SUCCESS / FAILURE ALERT
 → 09:15 BROKER OPENING BALANCE
 → INTRADAY / DELIVERY CAPITAL SPLIT
 → LOCK DAILY CAPITAL BASIS
 → TRADING
```

Daily margin snapshot:
- authoritative sizing reference for the day.

Order-time broker API:
- final execution safety/validation authority;
- may reject/adjust the proposed order.

If neither DB nor API provides usable margin information:
- use 100% cash requirement / zero assumed leverage;
- proceed;
- send mandatory incident alert;
- do not invent leverage.

Daily capital:
- is based on the 09:15 opening balance;
- remains locked for the day;
- reconciliation may detect/report drift;
- reconciliation must not rebase today's sizing capital;
- next trading day obtains a new opening balance.
