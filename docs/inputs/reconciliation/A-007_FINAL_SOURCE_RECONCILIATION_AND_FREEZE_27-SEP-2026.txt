6. MIS / INTRADAY
FACT: MIS maps to INTRADAY; intraday capital treatment exists; MIS is eligible
for emergency/EOD flatten; dedicated MIS auto-squareoff/EOD handling exists.
HISTORICAL USER EVIDENCE: MIS actually traded and was intended to close same day.
HISTORICAL USER EVIDENCE: intraday margin differed by stock/category.
Legacy leverage_map value 5.0 is documented as legacy implementation behavior,
not a universal V2 margin rule.

7. CNC / DELIVERY / GTT
FACT: CNC maps to DELIVERY; CNC is deliberately absent from the emergency
flatten set; EOD intraday squareoff does not flatten CNC; Delivery has a
broker-side GTT path; CncGttMonitor reconciles broker GTT state.
HISTORICAL USER EVIDENCE: CNC/Delivery actually traded; GTT worked correctly;
Delivery could remain overnight; manual exits were possible; manual exits were
later detected/reconciled by cnc_gtt_monitor.

8. CO / COVER ORDER
FACT: CO maps to COVER_ORDER; dedicated CO protocol exists; CO uses broker
variety "co"; CO has dedicated cancellation/squareoff handling and is in the
emergency flatten set.
HISTORICAL USER EVIDENCE: user remembers automated intraday TGT/SL behavior but
cannot recall whether the actual legacy entry mechanism was CO or BO.
FINAL CLASSIFICATION: actual historical CO use UNKNOWN / NOT ESTABLISHED.

9. BO / BRACKET ORDER
FACT: BRACKET_ORDER exists internally; legacy leverage-map entry exists;

FINAL CLASSIFICATION: actual historical BO use UNKNOWN / NOT ESTABLISHED.

11. PRODUCT VS ORDER TYPE / VARIETY
Product is distinct from MARKET/LIMIT/SL/SL-M. Repository order paths carry
intent and entry_order_type. CO handling uses variety="co" while regular
modification uses variety="regular". Exact historical compatibility matrix
and universal enforcement are UNKNOWN and are carried to Order Processing.

19. CURRENT ZERODHA CROSS-CHECK — NOT LEGACY EVIDENCE
Current official Zerodha material says CO is intraday-only and BO was disabled

20. FINAL LEGACY STATEMENT
The legacy system supported a semantic product model separating INTRADAY,
DELIVERY, COVER_ORDER and BRACKET_ORDER intents from broker product codes.
MIS represented INTRADAY, CNC represented DELIVERY, CO represented COVER_ORDER,
and NRML was recognised as DELIVERY. MIS and CNC were actually traded according
to user historical evidence; Delivery/CNC used a broker-side GTT protection
path and was excluded from intraday/EOD flattening; MIS had intraday squareoff
handling. CO and BO implementation existed, but actual historical Production
use of either could not be established, and NRML use also remains unestablished.

21. FUTURE V2 INPUTS PRESERVED
- Delivery: use GTT as intended broker-managed protection/exit mechanism.
- Intraday: select one suitable current Zerodha-supported mechanism; do not
  blindly carry BO/CO from legacy.
- Config.yaml proposed as master segment control: INTRADAY/DELIVERY/BOTH.
- Strategy YAML proposed as secondary control: ON/OFF, classification,
  LONG/SHORT; avoid global/strategy collisions.
- V2 LIVE-only.
- Intraday margin must use current broker/product/stock eligibility and
  actual margin data, not fixed legacy leverage.
- System should square off intraday before broker/RMS cutoff and verify;
  exact timing/state machine remains open.
- Delivery should not be treated as intraday auto-squareoff.
- Proposed V2 rule: one symbol once per day only.
- Protective-leg lifecycle, cancellation and partial-fill handling require
  explicit state-machine design.
