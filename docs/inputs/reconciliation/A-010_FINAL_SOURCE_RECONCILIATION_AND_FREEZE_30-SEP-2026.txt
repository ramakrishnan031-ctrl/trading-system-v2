## 2. FINAL RECONCILIATION

### Secret/configuration boundary — FACT
- YAML/configuration files contain business/system settings and credential references.
- Actual credentials/tokens/passwords were maintained outside tracked configuration, primarily through the VM environment/.env.
- `accounts.csv` contains broker-account metadata and environment-variable references, not the actual secret values in the reviewed repository.
- `.gitignore` excludes `.env` and credential artifacts.
- `core/config_loader.py` explicitly does NOT read `.env` and does not perform environment-variable interpolation; individual consumer modules read environment variables.

### Credential categories — FACT + USER CONFIRMATION
The user confirms the .env contained operational credentials including Zerodha API/authentication material, Telegram, email/SMTP, Chartink/webhook-related credentials and other operational secrets. Actual values are intentionally omitted.

### Account model — FACT + USER CONFIRMATION
Multiple Zerodha account metadata/credential-reference records existed. The user confirms only the active trading account was populated/used through the VM environment for actual trading. Inactive metadata was not recalled as being used for real trading.

### Environment loading — FACT / UNKNOWN
FACT:
- `core/config_loader.py` does not load `.env`.
- Telegram and SMTP consumers use environment-backed credentials.
- Security monitoring also uses environment-backed alert credentials.

UNKNOWN:
- Exact VM mechanism that injected `.env` values into the service process environment. User recollection points toward service/environment handling but is explicitly uncertain.

### Zerodha authentication — FACT / HISTORICAL / UNKNOWN
- Headless Zerodha authentication/token creation existed.
- A manual token creation/upload fallback existed.
- User recalls automatic cleanup of old tokens and creation of a new token during the next boot cycle; exact times are approximate and are not frozen.
- Exact authentication-failure recovery sequence is UNKNOWN.
- Exact effect of invalid authentication on existing-position management/reconciliation is UNKNOWN.

### Secret rotation / temporary files — HISTORICAL
User reports temporary plaintext files outside the repository were used to provide credential values to VS Code Claude for storage into `.env`, followed by deletion. Similar procedure was used for credential rotation. This is historical operator practice, not proof of secure governance.

### Direct .env editing — HISTORICAL / UNKNOWN
User reports occasional direct VM editing of `.env` through VS Code Claude. Exact restart/reload/rebaseline behavior is UNKNOWN.

### Git protection — FACT / UNKNOWN
- `.gitignore` excludes `.env` and credential artifacts.
- Repository documentation describes a pre-commit secret scanner.
- User does not know whether that scanner was consistently active historically.
- No secret values are reproduced.

### Historical exposure — USER-REPORTED
User reports no known credential leak was found, while accidental exposure/commit and credential rotation occurred historically. Exact incident evidence/timeline was not supplied, so this remains user-reported historical information.

### Security monitor — FACT
`scripts/security_monitor.py` watches sensitive security state including `.env`-related file hashes, SSH/authentication activity and copy-protection state. It can alert through Telegram and critical email/sentinel paths. It is an alert-oriented monitor, not an established pre-authorization gate.

### Copy protection — FACT / HISTORICAL
Repository security controls include VM↔PC copy-protection/audit mechanisms. User reports using the protected workflow. Complete historical enforcement for every transfer is NOT ESTABLISHED.

### Backup/retention — USER HISTORICAL
User reports no intentional independent backup store of .env/credential material. This was not independently verified.

### VS Code / Claude handling — USER HISTORICAL
Actual secret values were sometimes supplied through temporary files outside the repository so Claude could place them into `.env`; the temporary files were then deleted. This is documented as historical practice, not a security guarantee.

### Failure behavior — UNKNOWN except where directly confirmed
- Telegram unavailable: user reports fallback worked.
- Email failure: no observed incident; exact fallback UNKNOWN.
- Broker credential failure: no observed incident; exact behavior UNKNOWN.
- Missing environment variable at startup: exact behavior UNKNOWN.
