2. Core reconciliation

The user’s lifecycle summary is broadly supported:

BOOT → STARTUP CHECKS → RUNTIME/ENTRY WINDOW → POSITION MANAGEMENT → EOD/SQUARE-OFF → RECONCILIATION → SHUTDOWN

However, the repository contains a richer internal lifecycle than the
remembered operator labels STARTING and STOPPING. Production explicitly
implements startup scenarios COLD, WARM, CRASH, HALT, persistent kill
states INACTIVE, SOFT_KILL, HARD_KILL, persistent operational state,
startup reconciliation and clean-shutdown evidence.

Therefore “only STARTING and STOPPING” is retained as HISTORICAL
operator-visible labeling, not as the complete internal state model.

3. Lifecycle state reconciliation

Operator-visible state

-   STARTING during boot.
-   No remembered named READY/RUNNING state during normal operation.
-   STOPPING during shutdown.
-   Classification: HISTORICAL USER RECOLLECTION.

Internal startup scenarios — FACT

utils/startup_checks.py implements:

-   COLD: no session row / previous session is an earlier day.
-   WARM: same-day SHUTDOWN evidence, or completed EOD square-off can
    qualify a missing SHUTDOWN marker as a clean stop.
-   CRASH: same-day session with no SHUTDOWN marker and no qualifying
    completed EOD square-off.
-   HALT: active HARD_KILL, or same-day SOFT_KILL still active.

Source: utils/startup_checks.py, detect_startup_scenario() (around lines
192-360).

Kill states — FACT

-   INACTIVE: normal.
-   SOFT_KILL: blocks new entries; exits/monitoring continue; state is
    persisted first.
-   HARD_KILL: blocks orders and launches cancellation/flatten behavior;
    state persists.
-   resume(): explicit operator action, persisted/audited.

Source: capital/kill_switch.py, soft_kill(), hard_kill(), resume().

Critical distinction: SOFT_KILL is a trading-state transition, not
process shutdown.

4. Startup / boot

Production main.py contains, in order, the major boot stages:

1.  CLI parse.
2.  Weekend/holiday guard.
3.  Service START-window guard.
4.  Logging/config/environment initialization.
5.  State/database initialization.
6.  KillSwitch load and stale/scheduled-kill handling.
7.  Startup scenario detection.
8.  Configuration/startup checks.
9.  Broker/token/instrument preparation.
10. Startup reconciliation.
11. Component construction/start.
12. Webhook server and health checks.
13. Startup completion event/session write.
14. Runtime loop.

Production startup checks collect blocking failures rather than silently
continuing. HALT is a blocking condition unless --resume is supplied.

Source: main.py; utils/startup_checks.py.

systemd — FACT

deploy/systemd/trading-system.service:

-   ExecStart=...main.py --mode live.
-   StandardInput=null.
-   KillSignal=SIGINT.
-   Restart=on-failure.
-   exit 0 does not restart.
-   exit 3/4/5 are prevented from restart.
-   exit 1/2 restart after 10 seconds.

Thus automatic Production service startup is established. Whether direct
python main.py was routinely used in Production remains UNKNOWN.

7. HALT / RESUME

Production startup scenario detection makes active same-day kill
conditions a HALT. Without --resume, main exits with code 4. With
--resume, it calls KillSwitch.resume(... resumed_by="operator").

systemd deliberately does not restart exit code 4.

Prior-day stale/scheduled kill clearing also exists, so “next day
automatically resumes” is conditionally true, not universal for every
emergency same-day kill.

8. Kill-switch triggers

FACTS from source include SOFT_KILL paths for: - critical clock skew; -
transient API-failure auto-trip; - daily-loss/EOD paths; - scheduled
force-close/EOD behavior; - other safety callbacks.

HARD_KILL exists and has broker flatten/cancel behavior; current
Production includes a circuit-breaker HARD_KILL path after configured
consecutive broker API failures.

The user’s remembered 14:45 SOFT_KILL is NOT frozen as the exact source
timing. Current Production source/config shows: - MIS protective cutoff:
15:09; - PASS_1 approximately 15:03; - PASS_2 approximately 15:06; - a
separate 15:15 force-close SOFT_KILL path.

Therefore the remembered 14:45 value remains HISTORICAL/UNCERTAIN.

9. Signal / queue lifecycle

signals/webhook_receiver.py establishes:

HTTP request → authentication → validation → KillSwitch check → queue capacity → expiry → SQLite signal row → in-memory queue

When KillSwitch is active, the webhook request is rejected. Thus there
is no need to invent a separate “webhook service stopped” state to
explain entry blocking.

signals/signal_processor.py uses a dispatcher + worker pool. On clean
stop it drains remaining in-memory queue items into the executor and
waits for workers.

UNKNOWN: what survives an abrupt crash that prevents clean queue
draining. The user’s guess that all queued signals were dropped is not
frozen as fact.

10. Broker authentication failure

Production has an explicit BrokerAuthError path:

BrokerAuthError → mark auth failure → invalidate/rename real token → prevent restart loop → later non-interactive live start fails until token refresh

The actual token value is not documented.

The user reports no actual failed headless-auth trading day. That is
HISTORICAL USER RECOLLECTION; the code path is independently
established.

Important: BrokerAuthError is explicitly excluded from the transient
API-failure counter. It is treated as an auth/configuration issue rather
than a transient connectivity outage.

Exact behavior for already-open positions during a broker-auth outage
remains UNKNOWN / NOT ESTABLISHED.

11. Database / persistent state

SQLite persists operational state including sessions, system events,
signals, orders, trades, capital ledger, kill-switch state and
reconciliation information.

Startup scenario detection reads persistent state. Clean shutdown writes
a SHUTDOWN event. OrderMonitor and OrderPlacer rehydrate relevant state.
Reconciliation runs before the signal pipeline.

Therefore persistent DB state is a FACT, but there is no single proven
statement that every state is reconstructed identically after every
possible restart mode.

12. Order / position states

The repository uses multiple persisted statuses, including:

PENDING_FILL, OPEN, PARTIAL, EXITING, CLOSED, CLOSED_MANUAL

and terminal order states such as:

CANCELLED, FAILED, EXPIRED, COMPLETE.

HARD_KILL treats OPEN/PARTIAL/PENDING_FILL as live exposure.

The user’s “all listed states existed” answer is therefore directionally
correct, but the implementation is a collection of related state
machines rather than one universal finite-state enum.

13. Intraday / Delivery lifecycle

Intraday — FACT

Signal → entry → live position → SL/target management → MIS/CO same-day
square-off.

Delivery — FACT

Signal → Delivery/CNC position → broker-side GTT handling/overnight
holding → GTT/manual exit → reconciliation.

orders/eod_squareoff.py explicitly excludes Delivery/CNC from normal EOD
square-off.

Delivery can therefore survive application process termination when
broker-managed GTT responsibility has been established, subject to the
remaining broker/reconciliation dependencies.

The user’s statement that the application does not necessarily need to
remain alive after GTT is broadly consistent with the architecture, but
universal historical dependency is not separately proven.

14. EOD / MIS square-off

orders/eod_squareoff.py sequence:

1.  SOFT_KILL to block new entries.
2.  Cancel pending intraday entries.
3.  Cancel pending intraday SL/TGT legs.
4.  Exit intraday positions.
5.  Verification/recovery.
6.  Preserve Delivery/CNC.

orders/mis_autosquareoff.py has the two-pass protective protocol:

-   PASS_1 around 15:03.
-   PASS_2 around 15:06.
-   protective cutoff 15:09.

A later 15:15 circuit-breaker force-close path also SOFT_KILLs and
delegates actual intraday closing to EOD square-off.

The user’s remembered 14:45/15:00-15:10 sequence is retained as
historical recollection, not exact frozen timing.

16. Crash / exception recovery

Production distinguishes CRASH from WARM using persistent
session/SHUTDOWN/EOD evidence.

systemd restarts exit 1/2 and does not restart exit 0/3/4/5.

Startup reconciliation precedes new signal processing.

Historical same-day crash/duplicate-order incidents were not recalled
with sufficient confidence, so those are UNKNOWN.

17. Clean shutdown

SIGINT/SIGTERM handlers set the shutdown event.

The _shutdown() path: - sets shutdown event; - drains active HARD_KILL
flatten worker within bounded external-stop grace; - stops signal
processing and other managers; - cancels pending ENTRY orders; -
disconnects live feed; - sends shutdown notification; - writes SHUTDOWN
event; - checkpoints WAL; - closes StateStore.

systemd deliberately sends SIGINT to select this clean path.

Therefore clean shutdown is demonstrably different from crash/exception
termination.

18. Weekend / holiday

The trading service performs a holiday/weekend guard before normal
startup and returns 0 without starting the trading runtime.

The cron subsystem is independent and each job has its own
scheduling/market_day_only behavior. The user’s blanket claim that all
background cron jobs always run on all weekends/holidays is therefore
NOT ESTABLISHED universally.
