3. SOURCE FINDINGS RELEVANT TO B-001
======================================================================

3.1 Main service unit
Source: `deploy/systemd/trading-system.service`

The repository unit declares:
- `Type=simple`
- `User=ubuntu`, `Group=ubuntu`
- `WorkingDirectory=/home/ubuntu/systems/trading-system`
- `EnvironmentFile=/home/ubuntu/systems/trading-system/.env`
- `ExecStart` invokes the virtual-environment Python interpreter and
  `main.py --mode live`
- `StandardInput=null`
- `KillSignal=SIGINT`
- `TimeoutStopSec=30`
- `Restart=on-failure`
- `RestartSec=10`
- `RestartPreventExitStatus=3 4 5`
- `WantedBy=multi-user.target`

Interpretation limits:
- `WantedBy=multi-user.target` makes the unit eligible for boot activation
  when enabled; it does not prove that it was enabled on the historical VM.
- `Restart=on-failure` is the systemd-layer rule, not the complete restart
  policy once the token watcher is considered.
- `StandardInput=null` indicates headless service operation.
- The `--mode live` argument is source text, not proof of actual execution
  or broker activity.

3.2 Token watcher
Sources:
- `deploy/systemd/token-watcher.service`
- `deploy/token_watcher.sh`

The watcher unit declares `Restart=always` and runs the shell watcher.
The script polls the main service and considers service state, last exit
status/date, token freshness, service time window, and crash restart count.
It may issue `systemctl start trading-system.service` if its conditions pass.

The source script describes a watcher window of 08:00–16:00 IST, requires
a fresh token for start attempts, and defaults to a maximum of three crash
restarts per hour. It treats today's clean exit, today's HALT, and today's
startup-check failure differently from prior-day exits.

These are source-defined rules. Actual enablement, running status, event
history, and historical start causality on production are NOT ESTABLISHED.

3.3 Start-window discrepancy
Sources:
- `main.py`, `_within_service_window` and the `main()` start guard
- `deploy/token_watcher.sh`, `within_service_window()`

The production code reference defines the main start window as
[08:00, 18:15) IST. The token watcher checks [08:00, 16:00) IST.
Do not merge these into one claimed legacy window. Record the discrepancy
and defer operational interpretation to the relevant lifecycle/operations
topics.

3.4 Cron
Source: `deploy/cron/trading-system.cron`

The canonical file includes:
- token cleanup at 05:00 daily
- token refresh at 08:15 Monday–Friday
- preflight jobs at 08:30, 09:14 and 09:15 Monday–Friday
- other independent monitoring, backup, EOD, retention, and reporting jobs

No inspected canonical cron line directly runs `systemctl start
trading-system.service`. The watcher is the source-defined component that
can request a service start based on token/window/state conditions.
Detailed scheduler reconciliation belongs to M-002 and the scheduler
manual, not a redesign decision in B-001.

3.5 Guarded clean exits
Source: `main.py`, `main()`.

The source checks the holiday/weekend guard and then the start-window guard
before ordinary logging and validated configuration loading. The guarded
holiday/out-of-window paths return exit code 0. Therefore, exit 0 or a
completed start command does not by itself mean the service initialized or
became ready to accept trading signals.

Detailed configuration, state, broker, reconciliation, workers, and readiness
remain owned by B-002 through B-007.
