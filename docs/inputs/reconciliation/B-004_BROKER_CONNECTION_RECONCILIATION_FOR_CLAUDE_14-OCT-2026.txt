3. SOURCE-VERIFIED FINDINGS

3.1 Adapter boundary
`broker/zerodha_adapter.py` documents `ZerodhaAdapter` as a typed wrapper over an injected Kite client, constructed once and injected into consumers. It translates Kite exceptions to internal broker exceptions. The module says it does not itself retry failed calls. Caller-specific retry behavior must be traced separately.

3.2 Startup token gate versus remote probe
The answer sheet asserts startup makes `kite.profile()` or `kite.margins()` as a synchronous connectivity probe and aborts if it fails. This is NOT established by the source excerpts reviewed. `main.py` live setup reads `data_store/session/zerodha_token.json`, aliases the account's API-key environment variable and access token into the environment, and builds the Kite client. Missing token file or missing credential environment variable takes a visible return-code-6 path. `scripts/zerodha_login.py::is_token_valid` checks local token metadata, not remote connectivity.

`broker/token_monitor.py` calls a supplied profile function periodically; that does not prove a startup probe. Finalize only after tracing the complete main.py call order through adapter construction, reconciliation, worker/feed startup and monitor startup. Until then mark the first remote API call and its position UNKNOWN / NOT ESTABLISHED.

3.3 Token file
` scripts/zerodha_login.py` sets `data_store/session/zerodha_token.json` as the default path. `load_token` returns None on OS/JSON errors. `is_token_valid(account_id, token_path)` checks loadability, account_id match, today's IST date and non-empty access_token. This is a local metadata gate, not a broker-side validity check. `save_token` writes account, broker, access_token, api_key, date, saved_at and expires_at, and attempts restrictive POSIX file/directory permissions; effective historical host permissions are not established.

3.4 Token generation
Both browser-assisted helpers (`scripts/zerodha_login.py`) and headless TOTP code (`scripts/auto_refresh_token.py`) exist. The headless script's header describes a weekday 08:00 IST schedule after a 05:00 cleanup. This is source-comment/config intent, not proof that the production cron ran at that time. Verify the cron registry and dated host capture.

3.5 Token monitor
`broker/token_monitor.py` documents a daemon thread, default 1800-second interval, profile calls, optional market-hours-only checking, paper-mode no-op, transient-error versus genuine-expiry classification, CRITICAL log/notification and injected expiry callback. It explicitly says it does not autonomously refresh tokens, close positions, call hard-kill or exit the process. The callback's actual main.py effects must be traced. Broker-resident accepted exit orders and new REST requests after auth failure are different cases; do not claim exits are guaranteed.

3.6 Exception translation
`broker/zerodha_adapter.py::_translate_kite_exception` maps:
- TokenException -> BrokerAuthError
- NetworkException -> BrokerTimeoutError
- InputException/OrderException -> OrderRejectedError
- PermissionException -> BrokerAuthError
- TimeoutError/socket.timeout -> BrokerTimeoutError
- GeneralException/unknown -> BrokerError

Therefore, a permission failure is not automatically token expiry, and a generic 403 must not be interpreted without context.

3.7 IP/permission handling
`broker/auth_recovery.py` classifies message text as IP_NOT_ALLOWLISTED, TOKEN_EXPIRED or AUTH_UNKNOWN and builds an IP-related alert. This contradicts the answer sheet's broad statement that no IP-allowlist handling existed in the codebase. It does not prove a real IP allowlist incident occurred or establish historical broker policy at every date. Separate source handling from actual incident history.

3.8 Paper/live
`main.py` sets `kite_client=None` in paper mode; live mode reads the token and builds a real Kite client. It constructs `ZerodhaAdapter` with the paper flag. The adapter header says paper mode simulates adapter calls and never touches the Kite client. Paper order operations use a local simulation path.

However, main.py also passes a `quote_provider` built by `_make_paper_quote_provider()`. Do not conclude that paper mode never reads token material or makes any external quote request until that provider is traced. The answer-sheet claim that the adapter itself instantiates a real KiteConnect/KiteTicker client in paper mode is contradicted in its broad form by the `kite_client=None` and no-Kite adapter contract.

3.9 Retry/rate limit
The adapter says it does not retry. Its documented HTTP 429 path penalizes/freezes a rate-limit bucket and raises; the documented caller owns retry. Do not generalize this to all callers or all operations.

3.10 Checked-in service unit
`deploy/systemd/trading-system.service` contains an EnvironmentFile, `ExecStart ... main.py --mode live`, `Restart=on-failure`, `RestartSec=10`, `RestartPreventExitStatus=3 4 5`, and journal output. This is checked-in config, not proof of the unit installed on the former production host.

3.11 Logging
The checked-in unit sends stdout/stderr to the journal; `.gitignore` excludes `logs/` and `*.log`. Do not claim exact files such as `logs/broker.log`, `logs/auth.log`, or specific DB table names exist unless verified in source or dated records. No historical journal/database was re-read in this review.
