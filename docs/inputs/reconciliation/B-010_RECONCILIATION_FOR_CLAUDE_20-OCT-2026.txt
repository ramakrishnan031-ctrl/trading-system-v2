3. IMPORTANT QUALIFICATIONS / RECONCILIATION
A. Entry-gate correction to frozen B-009
CONFIRMED SOURCE DEFECT / DOCUMENTATION ERRATUM:
The B-009 statement that the 15:17 routine clears the entry gate is incorrect for the pinned baseline. _fire() only clears the gate when one was passed into EodSquareoff. main.py's constructor call does not pass entry_gate. The clear step is therefore inert in the wired path. This does not overturn B-009's separate finding that no runtime caller feeds fresh candidates into EntryGate.add(); only the claim that EOD clears stored gate entries needs correction.
Governance: do not edit the frozen B-009 manual silently. Record an approved erratum against B-009/DR-046, and amend only after Rama approves the erratum workflow.

B. MIS Telegram alert defect — precise scope
CONFIRMED SOURCE DEFECT:
The MIS unit's direct _notifier.send(...) call uses the unsupported keyword message and omits required body/source_module. That direct send attempt raises and is caught/logged. However, main.py also wires a separate critical_sink to MisSquareoffNotifier, which is invoked before the direct notifier call. Therefore do NOT say that all MIS critical alerts or the separate notifier path are necessarily broken. Source establishes the direct call mismatch; actual delivery on a given date remains UNKNOWN / NOT ESTABLISHED.

C. EOD pending-entry cancellation defect
CONFIRMED SOURCE PATH:
The EOD query selects status PENDING_FILL, while OrderPlacer attempts PENDING before the broker call. The reviewed source search reports no runtime update back to PENDING_FILL. Therefore the EOD query can miss resting entry orders that have transitioned to PENDING. Do not overstate that no entry cancellation happens at 15:15: that is a separate OrderMonitor path and its effect depends on that monitor running. Actual host state is unknown.

D. EOD MARKET orders and protection
CONFIRMED SOURCE FACT:
The examined EOD MARKET fallback calls omit market_protection; the adapter omits a protection field when none is provided. The record-backed reports of broker rejection are separate historical evidence. Phrase operational outcome conditionally: the source path is vulnerable to rejection under the documented broker constraint; this review does not establish that the baseline code ran on a given date.

E. COMPLETE persistence gap
CONFIRMED SOURCE PATH, based on Claude's cited state_store ranges, pending full independent line-by-line recheck if needed:
The COMPLETE UPDATE does not check affected-row count. If the write-ahead insert failed but the UPDATE returns successfully with zero rows changed, the exception fallback will not run, and no COMPLETE row may exist. Label the possible subsequent recovery fire as an interpretation, not a witnessed event.

Keep these separate from general EOD:
- The source describes PASS 1 as MARKET with a 1.5% protection band and PASS 2 as MARKET with a 2.5% band; the module header's LIMIT_THEN_MARKET wording is documentation drift.

- Protection restoration and post-pass verification are source paths, not evidence of successful operation on the host.
