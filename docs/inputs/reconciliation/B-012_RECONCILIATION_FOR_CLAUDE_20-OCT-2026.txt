1.1 Main service unit
`deploy/systemd/trading-system.service` at the pinned commit declares `Restart=on-failure`, `RestartSec=10`, and `RestartPreventExitStatus=3 4 5`; it declares no explicit `StartLimitIntervalSec` or `StartLimitBurst`. 1.2 Token watcher
`deploy/token_watcher.sh` confirms a 30-second polling loop by default, a 300-second long sleep, crash-count threshold 3 per rolling hour, fresh-token requirement, and the service window 08:00 inclusive to 16:00 exclusive IST. Therefore “08:00–15:59” is a readable clock-time rendering, not a separately configured end time. Its state table treats same-day exit 4 (HALT) and exit 3 (startup-check failure) as no-restart cases; prior-day cases may be retried when the token and time guards pass. Exit 1/2/other failed-state codes use the watcher’s capped recovery branch. Inactive state has separate clean-exit/date handling.

Important qualification: the watcher’s three-per-hour limit is not the same mechanism as systemd’s own `Restart=on-failure`. The source does not establish that the watcher cap limits every automatic systemd restart attempt while the unit itself is repeatedly restarting. Describe each supervisor independently and leave actual host behaviour unknown.

2. WORDING / SCOPE ADJUSTMENTS REQUIRED IN THE MANUAL

A. Do not write “systemd restarts forever/unlimited” as an unconditional fact. Write: “The unit declares on-failure restart after 10 seconds and has no unit-local StartLimit directives; effective manager defaults/drop-ins and installed state are not established by this source snapshot.”

B. Do not collapse the systemd restart policy and token-watcher cap into a single cap. The token watcher has a three-per-rolling-hour branch for its own start decisions; systemd has a separate on-failure policy. The interaction under repeated crash loops is conditional and depends on service state, systemd rate limiting, and installed configuration.

C. “The watcher restarts at most three times per hour” should be narrowed to “the watcher records/limits its own crash-branch start attempts to three per rolling hour.” Its source checks `ActiveState`; if systemd itself is already restarting the unit, the watcher can see `activating` and wait. Do not infer a global restart ceiling from the watcher constant alone.

D. The drill’s SUCCESS heartbeat defect is confirmed in source. Keep the result and execution status distinct: report verdict / return code indicates drill result; default heartbeat status does not. Whether a particular monitor raises or suppresses an alert depends on consumer logic and should not be asserted unless separately source-verified.

E. Use exact 08:00–16:00 IST window, with 16:00 excluded. “Only between 08:00 and 15:59” is equivalent for minute-resolution prose but less exact.

F. Do not imply backups contain the complete recoverable system. The checked-in jobs cover main DB, analytics DB and evidence-job invocation; evidence destination was not traced. The records show same-volume backups and one dated manual off-box copy, not a verified current offsite recovery point. Token/session file, `.env`/secrets, logs, marks, and installed host state are not shown as part of the database backup jobs.

G. “Restart after a kill is blocked until the next day” needs the exact state distinctions:
- Same-day HARD_KILL -> HALT; manual `--resume`/operator recovery required.
- Same-day emergency SOFT_KILL -> HALT unless the separately coded scheduled-kill/no-open-position condition applies.
- Prior-day kill clearing is performed on startup; it is not evidence that the service starts successfully.
- If the process remains alive past the expected self-exit, the ordinary new-process startup clear path has not run; cross-reference B-011.

H. A successful `--check` / cron drift pass verifies the installed crontab’s lines against the generated registry lines at that moment, not job success. Keep configuration, monitoring evidence, and actual execution as separate evidence classes.
