2. MATERIAL FINDINGS THAT MUST REMAIN VISIBLE
A. Queue construction: one in-memory standard-library Queue, maxsize 300; receiver and processor share it.
B. Backpressure is per request at qsize >= 240; warning header threshold is 180. A request may still reach a full queue after passing the request-level check.
C. The database row is committed as QUEUED before first enqueue. A put failure may therefore leave a row without an item if the status update also fails.
D. Receiver retry for an existing QUEUE_FULL row puts the item before updating the row to QUEUED; the status update is unconditional and failure is only logged. This is a source-path race/inconsistency, not a proven incident.
E. Three re-queue paths are present in source, but the FIX-007 rate-limit pre-check is not wired by main.py at the pinned commit. The placement re-queue path is separate.
F. Dispatcher submits to a five-worker executor without waiting for a free worker. Queue depth does not include work already submitted to the pool.
G. Clean stop drains the queue into the pool, but REJECTED_SHUTDOWN is written at the placement check only; earlier stages may reject with another status. A late enqueue after final drain is a possible unprocessed item, not an observed event.
H. The in-memory queue is lost on crash. The bounded searches found no restart path that re-enqueues QUEUED rows. Do not broaden that to an absolute proof about every uninspected mechanism.
I. B-007's /metrics queue fields fixed at zero are re-verified as a known defect.
J. Test sources are documentary evidence only; none was run. No production occurrence or sender retry is established.
