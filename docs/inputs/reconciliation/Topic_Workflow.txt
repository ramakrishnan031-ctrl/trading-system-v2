1. AUTHORISATION IS TOPIC-BY-TOPIC, NOT WHOLE-AGENDA AUTHORISATION

Rama authorises Claude to work continuously through the currently active agenda topic,
within that topic's approved scope and governance, without stopping for routine permission
after each small task or deliverable.

This is NOT authorisation to execute all remaining agenda topics in one uninterrupted run.
When the current topic is completed and published, Claude must stop before beginning the
next topic and wait for the new topic-start package/instruction from ChatGPT.

The next topic starts only after ChatGPT prepares and provides its topic-specific files and
explicitly hands that topic to Claude. Do not independently start the next topic, even if
the agenda lists it as the next item.

2. CHATGPT PREPARES THE START PACKAGE FOR EVERY TOPIC

Before Claude starts a new agenda topic, ChatGPT will prepare and provide the applicable
starter materials. These may include:
- Rama answer sheet / questions requiring Rama's personal decisions or preferences;
- Claude research and execution prompt;
- topic scope, objectives, boundaries, dependencies and exclusions;
- source inventory / permitted-source instructions;
- required evidence and output expectations;
- relevant prior decisions, open questions and cross-topic dependencies;
- any other file(s) ChatGPT considers necessary for a complete, controlled investigation.

Claude must read and follow the complete start package before beginning. If a required
starter file is missing, unreadable or contradictory, identify the issue before crossing
the affected boundary. Do not substitute a generic short questionnaire for the topic
package.

3. DISTINGUISH FACTUAL/HISTORICAL QUESTIONS FROM RAMA-PREFERENCE QUESTIONS

A. SYSTEM-BEHAVIOUR / HISTORICAL-FACT QUESTIONS
Examples: how pre-flight runs; what checks it performs; how soft-kill is initiated; what
conditions trigger it; what happens after a specified number of consecutive losses; how
startup, scheduling, order processing, reconciliation or recovery actually worked.

For these questions, do not ask Rama to remember or guess the implementation. Use the
authorised primary evidence for the topic (for example, the designated legacy repository,
source files, configuration, database/schema records, logs, tests, deployment records or
other explicitly permitted historical evidence). Trace source -> input -> logic -> guard/
validation -> output -> storage/handoff -> next consumer wherever evidence allows.
Record exact file/function/line/config/table/API references where available. Distinguish
FACT, HISTORICAL, UNKNOWN / NOT ESTABLISHED, INTERPRETATION and KNOWN DEFECT.
Do not invent missing behaviour or silently repair the historical description.

IMPORTANT SOURCE GOVERNANCE: Legacy production systems are DEAD / REFERENCE ONLY.
Legacy source, clones, hosts, VMs, runtime, broker or databases may be inspected only when
the active agenda's explicit source permissions and governance authorise that access.
A topic-specific instruction or general example in this workflow does not override a
source prohibition, Route B / W-11 / option C boundary, security restriction or other
established decision. If the required evidence source is prohibited or not authorised,
record UNKNOWN / NOT ESTABLISHED, explain the exact evidence dependency, and ask for
the necessary scope decision. Do not access it anyway.

B. RAMA'S PERSONAL PREFERENCES / USER DECISIONS
Examples: preferred trading hours; preferred operating method; whether orders should be
cancelled after a stated loss sequence; acceptable user-facing behaviour; chosen
risk/operational preferences.

These must be answered by Rama. ChatGPT may help phrase the question and explain
consequences, but must not invent a preference or decide on Rama's behalf. Put such
questions in the answer sheet and ask them clearly, with enough context to make a
meaningful decision.

C. MIXED QUESTIONS
Separate objectively verifiable system facts from Rama's desired future behaviour.
Research the historical fact from authorised evidence; ask Rama only for the preference
or decision. Never conflate what the old system did with what Rama wants the new system
to do.

6. REVIEW GATES — DO NOT PUSH IMMEDIATELY AFTER DRAFTING

The publication sequence is mandatory:

a. Claude prepares the complete local topic package and checks its internal consistency.
b. A separate Claude reviewer, who did not draft the package, independently reviews it
   under the established W-12 rule. Record reviewer, findings, severity and resolution.
c. Claude resolves findings and prepares the revised complete package, but DOES NOT PUSH.
d. Claude sends ChatGPT the complete pre-push package/review evidence and a concise
   change/inventory report. Ensure ChatGPT can inspect the actual files, not merely a
   summary or screenshot.
e. ChatGPT performs an independent pre-push audit for completeness, factual support,
   source traceability, Rama-answer attribution, governance, consistency, missing
   artefacts, cross-topic dependencies and repository uniformity.
f. If ChatGPT requests revisions, Claude makes them and returns the revised package for
   re-review. Repeat only as necessary.
g. Claude may push to the designated V2 GitHub repository ONLY after ChatGPT explicitly
   says the package is OK TO PUSH. Silence, a partial review, an independent Claude PASS,
   or a local commit is not permission to push.
h. After the push, verify the remote and a fresh clone byte-for-byte as required by the
   established repository publication rules. Save the post-push verification record and
   carry forward the exact push line to the next topic's package.

Do not push to an alternative branch or repository to bypass this gate. Do not claim
publication until remote and fresh-clone evidence confirms it.
